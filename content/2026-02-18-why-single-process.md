做这个站之前我给自己定了一条约束：**一台机器、一个容器、一个数据文件**。

## 为什么探测必须放在服务端

一开始我想过在前端直接 `fetch` 内网系统的地址，看起来最省事。但这条路走不通，原因有三条：

1. 浏览器的同源策略会挡掉跨域响应，除非每个内网系统都愿意配 CORS；
2. 前端探测是「有人打开页面才探」，凌晨没人看的时候那段历史就永远是空白；
3. 站点一旦部署在内网之外，浏览器根本碰不到 `10.x` 开头的地址。

所以探测只能由部署这台站点的机器发起。它的位置就是监控的位置——这也是选择自托管而不是静态托管的关键原因。

## 为什么不用前后端分离

这个站只有两类页面：内容页和一个面板。前后端分离能带来的好处（独立扩缩容、前端团队并行开发）在这里一项都用不上，代价却是多一套构建、多一个容器、多一层联调。

用服务端渲染直接出完整 HTML 的好处很实在：

- 首屏不用等 JS 下载和执行；
- 没有 hydration，也没有「白屏转圈」；
- 整站只有一份依赖树，升级不用对齐两边。

面板需要自动刷新，那就只给这一页加一小段原生 `fetch`，30 秒拉一次 JSON 局部更新，不引入任何框架。

## 数据怎么存

可用性历史用 SQLite。每分钟一轮、几十个目标，一天也就几万行，用任何时序数据库都是杀鸡用牛刀。SQLite 的好处是：

- 单文件，直接挂 Docker volume；
- 零运维，没有额外容器；
- `WAL` 模式下读写不互相阻塞，探测写入和页面查询可以并行。

> 判断标准很简单：如果一张表的增长量级是「每天几万行、保留 30 天」，那就不要为它单独部署一个数据库。

## 一个容易踩的坑

探测时我只读响应头，然后立刻取消 body：

```js
const res = await fetch(url, { signal: controller.signal })
await res.body?.cancel()
```

原因是有个内网系统在 502 时会返回一个巨大的错误页，如果把 body 读进内存，探测进程的内存曲线会跟着对方的故障一起抖。
