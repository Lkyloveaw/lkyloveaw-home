# 编辑器形态定稿：富文本（结构化文档 + 服务端渲染）

本文件是「编辑器形态」这张票的产出（map：[文章后台 #30](https://github.com/Lkyloveaw/lkyloveaw-home/issues/30)）。

相关：[#32 真源](https://github.com/Lkyloveaw/lkyloveaw-home/issues/32) · 规格 [#48](https://github.com/Lkyloveaw/lkyloveaw-home/issues/48)

## 1. 要回答的问题

这个站的文章编辑器该是哪种形态：**纯 Markdown 文本域 + 服务端预览** / **分栏实时预览** / **富文本**？
两把尺子：① 在**中文长文 · 表格 · 代码块 · 图片**四件事上的**手感**；② **无构建步骤**下的**实现代价**。

原型（抛弃分支 `prototype/editor-shape`）只换「编辑区那一块」，页头页脚与样式复用产品的 `layout()` 与
`public/style.css`，预览走**真的** markdown-it（与 `src/content.ts` 同参）与**真的** gray-matter ——
所以三个变体是在真实排版密度下被比较的，不是三个空壳。

## 2. 三个候选争的是「第一等公民是谁」

| | 变体 | 第一等公民 | 需要 JS | 预览来自 |
| --- | --- | --- | --- | --- |
| `A` | 纯文本域 + 服务端预览 | **我提交的那一版** | 否 | 服务端 markdown-it |
| `B` | 分栏实时预览 | **我正在写的那一句** | 是 | 服务端 md（防抖 POST 回填） |
| `C` | **富文本（所见即所得）** | **读者将看到的样子** | 是 | 屏幕上就是最终形态 |

## 3. 赢家：`C` —— 但它是**代价最大**的那个

用户看过三个变体的实机原型后选 **C**。

**它赢在**：写作时不用在脑内做一次「Markdown → 渲染结果」的翻译；表格、代码块、图片的操作都是直接的。

**它贵在**：C 是三个里**唯一同时推翻三条既有约束**的那个，而且推翻得**不可悄悄进行**（§4）。
这不是「C 更好」，是**用户明确选择了用手感换代价**——这句话得写在最前面，免得后来者以为这是笔划算的交易。

## 4. 它推翻了三条已定的事（显式修订，不偷偷改）

| 被推翻的 | 出处 | 现在的决定 |
| --- | --- | --- |
| **`body` 是 Markdown 源**（不是渲染后的 HTML） | [#32](https://github.com/Lkyloveaw/lkyloveaw-home/issues/32) 的决定 + 规格 [#48](https://github.com/Lkyloveaw/lkyloveaw-home/issues/48) 的表结构 | 正文改存**结构化文档 JSON**（§5）。**触发点**：用户要**合并单元格与列宽**，而 Markdown 的表格语法（GFM）只能表达**规整网格**——X 列 Y 行 ✓、对齐 ✓，合并 ✗、列宽 ✗、单元格内多段 ✗ |
| **无构建步骤 + 尽量不引依赖** | map #30 Notes 的「既有约束延续」 | 为**编辑面**引入前端构建步骤与 WYSIWYG 依赖（ProseMirror / TipTap）。见 [ADR 0006](adr/0006-frontend-build-step-for-richtext.md) |
| **禁用 JS 也能写**（写路径 = 纯表单 POST） | `docs/article-write-api-decision.md` §5.2 | **写需要 JS**。**读面不受影响**——首页 / 列表 / 文章页仍是服务端渲染，禁用 JS 照样读 |

## 5. 正文存什么、怎么渲染（本次新定的核心）

**存编辑器自己的文档（ProseMirror / TipTap JSON）；读面用同一套 schema 在服务端生成 HTML。**

**为什么不是「存 Markdown」**：用户要合并单元格与列宽，GFM 表达不了（§4）。
若坚持 Markdown，就得每次保存都过一次有损转换器，而**表格正是它丢东西的地方**——
原型实测：同一份转换器在样本上「表格 5/5 保住」，换一份输入就 **5 行 → 0 行**。
富文本 + Markdown 源的组合意味着「你看到的样子」和「存下来的样子」之间永远隔着一个会变形的转换器。

**为什么不是「存 HTML」**：存 HTML 就要在读面渲染我们存下来的 HTML 字符串，
`markdown-it` 的 `html: false` 那道「**不可信输入不直接进页面**」的保证就没了，
必须换成服务端白名单 sanitizer —— 而那是本仓风险最高的一类代码（手写必有漏，引库又多一条依赖）。

**存文档 JSON 保住了那条属性，只是换了个方式**：
读面渲染出的 HTML 由**闭集 schema** 决定，而不是由库里那个字符串决定。配套的硬约束是——

> **schema 里不启用 raw HTML 节点。** 这样编辑器自己也造不出任意 HTML，
> 读面可渲染的标签集是**闭集**，与今天 `html: false` 的效果等价。

这与仓库现有精神一致：**源是结构、渲染在服务端、不可信输入不直接进页面**。

## 6. 代价与连带（写在明面上）

- **构建步骤 + 依赖**：打包产物只服务编辑面，但仓库从此有了一条构建流水线（ADR 0006）。
- **写需要 JS**（读面不需要）。`#33` §5.2 的「禁 JS 仍可写」已在其文档里加横幅修订。
- **首次导入要多一跳**：既有两篇 Markdown → （markdown-it）HTML → （schema 解析）文档。
  这是一次性的、近似的，与 #32 的「首次导入」同一条规则（导完文件被忽略、只打警告）。
- **修订表快照存文档 JSON**（#32 决定的「全文快照」不变，只是格式跟着走）。
- **编辑器渲染与读面渲染必须靠同一套 schema 对齐**；但两边 CSS 仍可能不一致
  （WYSIWYG 显示的是编辑器样式，读面是产品样式）——这是实现期要盯的风险，不是「长得一样」的保证。
- **表格的能力边界仍受存储之外的东西约束**：嵌套表、跨文档引用等由所选库的 schema 决定，本期不承诺。

## 7. 验证

**原型阶段**（由另一个会话产出，**我在干净的 worktree 里独立复现过**）：

| 检查 | 结果 |
| --- | --- |
| 它自己的验证脚本 | **52 通过 / 0 失败**（我重跑，逐节一致） |
| 三个变体结构不同 | ✅ 按代码真标记核：A `pv-textarea` · B `pv-grid` · C `contenteditable` |
| 产品文件零污染 | ✅ `git diff` 对 `server.ts`/`auth.ts`/`views.ts`/`style.css`/`content.ts` **输出为空** |
| 服务端渲染耗时 | 样本 5738 字节 → `0.61 / 1.01 / 1.62 ms`（markdown-it 不是瓶颈） |

**一条我复核时发现并修正的文档缺口**：坑原型 `NOTES.md` §5 把硬骨头用例的损失写成 3 条，
实测那份输入的损失报告是 **5 项丢 / 6 项**（表格行 5→0、围栏 2→0、语言标注、引用块 1→0、front-matter）。
这条是 §5「为什么不是存 Markdown」的**更硬的证据**，已写进票 #34 的评论。

## 8. 未验证（诚实登记）

- **没有浏览器 PoC**。原型的客户端交互（防抖预览、切变体带正文、键盘切换、工具栏、存回 Markdown）
  只在页面上断言过**存在性**，**没人在浏览器里点过**；窄屏断点与浅色模式也没测。
- 原型用的是 `contenteditable` + **`execCommand`（已被标准废弃）** 的脚手架，**不是成品路线**；
  成品要上的库（ProseMirror / TipTap）在本仓**一行都没写过**，其构建、扩展集、服务端渲染都**未验证**。
- 「表格合并单元格 / 列宽」在所选库的 schema 里**能不能一次到位**，本文只声明**目标**，未做 PoC。
