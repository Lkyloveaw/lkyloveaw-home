### 0.1 这条边界画在哪：**「改错了会不会动数据 / 锁人」**

搬进库的门槛是三条**都**满足：

1. **它只影响渲染或节奏**（标题、描述、探测间隔）；
2. **改错了当场看得出来**（标题错了页面上就是错字；间隔错了下一轮日志里就能看出频率）；
3. **不需要先有另一条通道才能救**（不存在「网页改坏了、只能 SSH 进去改回来」）。

按这三条过一遍，`PROBE_RETENTION_DAYS` 与 `BACKUP_KEEP` 就落在门外：
它们**会删数据**，而且「删错了」是**事后才发现**的——这正是本仓反复防的那类形状
（`store.ts:120-130` 的 `busy` 校验、`backup.ts` 的产物校验都是同一个精神：
**正在删东西的动作不能靠返回值骗自己**）。把它们放进一个网页表单，
等于给「删光备份」加了一个两次点击的入口。

**数据库真的可读吗**：`data/availability.sqlite` 就在站点旁边，任何能读它的人都已经拿到
`password_hash`、目标 URL 与全部历史（`docs/session-revoke-decision.md` §1 对同一个问题给过同样的判断）。
所以「密钥不进库」的理由**不是**「库更不安全」，而是**分层**：
密钥属于进程的启动配置，改它必须重启；而标题属于内容，改它应当立即生效。

## 1. `settings` 表

```sql
CREATE TABLE IF NOT EXISTS settings (
  key        TEXT PRIMARY KEY,
  value      TEXT NOT NULL,
  updated_at INTEGER NOT NULL
);
```

**为什么是 key-value，不是「一行多列」**：已知的设置是 3 个（今后可能 5～6 个），
且**类型各异**（两个字符串 + 一个整数）。一行多列的表在**每次加设置时都要 `ALTER TABLE`**，
而 key-value 加设置只需在代码里加一行白名单。代价是「取出来是文本，要显式转换与校验」——
而这一步本来就是必须的（§3），所以不额外付成本。

**为什么白名单在代码里、不在库里**：合法键的集合是**这个程序理解的键**，
不是「库里恰好有哪些行」。库里出现一个代码不认识的键（手工加的行、旧版本留下的），
正确行为是**忽略它并在启动时警告**，而不是把它渲染到页面上。

**没有 `updated_by` 列**：改设置的是管理员，而「谁改的」属于**审计**——
map 迷雾里那条（`Not yet specified`）明确说它还不够锐利，不在本票升票。
真要做审计时，它是 `settings` 旁边的一张日志表，而不是这一列。

## 2. `.env` 与 DB 谁优先：**一次性的 DB 优先**

**【默认】读值顺序：DB → `.env`（已解析）→ 代码默认值。首次启动把「当前生效值」写进 DB，
此后 `.env` 完全不再参与这个键。**

```
启动（initSettings()）：
  for 每个白名单键 k:
    若 DB 里没有 k 的行:
         resolved = env 值 ?? 代码默认值
         INSERT INTO settings VALUES (k, resolved, now)
         日志：把 k 的生效值固定为 resolved（来源：env / 默认值）
    否则:
        若 env 里存在 k 且与 DB 值不同 → console.warn（说明 env 被忽略、真源是数据库）
```

**为什么不做「`.env` 永远优先」**：那等于网页上的保存按钮在下次重启后**悄悄失效**——
用户改了标题、重启、发现改回来了，且没有任何提示。这是最坏的一类失败（静默 + 反复）。

**为什么不做「谁最后改谁优先」**：那需要记录每次改动的时刻，还要用户自己记住
「我上次是在网页改的还是改的 env」——把一条规则变成一道记忆题。

**为什么不做「DB 里没有才读 env」（纯 fallback，不落库）**：那样「DB 里没有」永远是未定义状态，
用户没法「把标题设回默认值」——他删掉行反而会退回 env 值。

**那条 `console.warn` 是配套的**（与 `#26` §2 的「文件被忽略」警告同一形状）：
静默忽略 env 才是最难排查的。文案要说清三件事：**这个键已被数据库接管、env 值被忽略、要改去管理台**。

**迁移是一次性且幂等的**：`INSERT` 只在键不存在时发生；重复启动不会改动任何已有值
（这也意味着**升级不会覆盖用户在网页上改过的任何东西**）。

## 3. 校验：闭集键 + 逐键规则

| 键 | 类型 | 规则 | 越界时 |
| --- | --- | --- | --- |
| `site.title` | string | `trim()` 后长度 1–60 | **400** + 就地重渲染（`#23` §4.2） |
| `site.description` | string | `trim()` 后长度 0–200 | 400 |
| `probe.intervalSeconds` | integer | 5 ≤ n ≤ 86400 | 400，文案给出区间 |

- **键是闭集**：写路由的 `action`/字段名走 `#25` §5.3 的闭集判定，未知键 → 400。
- **值一律当字符串入库**，读的时候按上表的类型转换。**转换失败 = 数据坏了**，
  此时**回退到默认值 + `console.error`**（不是静默用 NaN 跑下去）。
- **`probe.intervalSeconds` 下界取 5 秒**（【默认】）：内网个人站，1 秒一探对被监控系统不友好，
  而 5 秒已经足够「实时」；上界 86400（一天）比「不小心填了 0 导致探测停摆」多点余地——
  ⚠ 注意今天 `num()` 的语义是「**非正数就回退默认**」，所以 `.env` 里 `PROBE_INTERVAL_SECONDS=0`
  会得到 60 秒；DB 里则**拒绝** 0，而不是悄悄回退。两者不一致是对的：
  env 是启动期的容错，网页表单是**有人正在看着的输入**，该说的是「这个值不行」。

## 4. 改探测间隔要立即生效吗：**是，下一轮就用新值**

**【默认】探测循环每一轮**在 `setTimeout` **之前**重新读一次间隔（`src/probe.ts:148` 那一行）：

```ts
// 今天：setTimeout(() => void tick(), config.probeIntervalMs)
// 之后：setTimeout(() => void tick(), getProbeIntervalMs())
```

**语义要说准：改完不会打断正在等的那一轮。** 换句话说，若当前间隔是 60 秒、这一轮刚结束、
定时器已经在等 60 秒，此时把间隔改成 10 秒 —— **下一次探测仍可能等满这 60 秒**，
之后每次都是 10 秒。这是**对**的行为（打断一个已经排好的定时器只会让「下一次探测什么时候来」
变得不可预测），但它必须**写在页面上**，否则用户会认为保存没生效：

> 页面上那行说明（`#23` §6.5 定的形态）：**「保存后从下一轮开始按新间隔探测；正在等的那一轮不会被打断。」**

**为什么不「保存即重启定时器」**：那需要跨模块操作 `probe.ts` 里的 `timer`
（今天的 `startProbing`/`stopProbing` 是进程级的，没有「重排下一轮」这个动作），
为一个「最多多等一个旧间隔」的体验引入一条新的控制路径不划算。

**为什么每次重读而不是缓存**：与 `#26` §6 同一条判断——一次单表主键 SELECT 是微秒级，
而缓存会引入失效逻辑与「改了不生效」的静默失败。

**`/status` 上那行「每 N 秒探测」**（`views.ts:406`，数据来自 `summary.probeIntervalSeconds`）
改成读**库里当前值**：它说的是「配置值」，而不是「刚过去那一轮的间隔」。
两者在改完后的一个间隔内可能不一致——这与上面那句说明是同一件事的两种呈现，不冲突。

## 5. 备份 UI 做到哪一步

今天已有：`listBackups()`（列出 `YYYY-MM-DD.sqlite`）· `runBackup()`（checkpoint → 备份 → **校验产物** → 滚动清理）·
`pruneBackups()`（留最近 N 份）· `verifyBackup()`（真的查一次 `probes` 表）。

**【默认】管理台的备份区块 = 列表 + 「立即备份一次」+ 两行只读的运维参数。**

| 做 | 不做 | 理由 |
| --- | --- | --- |
| 列出产物：文件名 · 大小 · 时间（倒序） | — | `listBackups()` 只给文件名，大小要 `fs.statSync`（一次目录里的几次 stat，量级可忽略） |
| 「立即备份一次」按钮 | — | map Notes 第 4 条点名。复用 `runBackup()`，它已经**先 checkpoint 再备份、并校验产物** |
| 显示今天是否已备份 | — | `runBackup()` 天生的行为：**今天已有一份且它能用就跳过**（`backup.ts:99-102`）。UI 要如实说「今天已备份过，本次跳过」，而不是假装成功（`#25` §7 的幂等表） |
| 只读展示 `BACKUP_DIR` 与 `BACKUP_KEEP` | 让它们可改 | §0.1 的边界：它们会决定文件去哪、删几份 |
| — | **下载产物** | `#23` §6.4 已判：整库含 `password_hash`，且站点还是 HTTP |
| — | 恢复 / 上传 / 删除单个产物 | 恢复是**最难、最危险**的动作（`backup-checkpoint-decision.md` §7 有实测的恢复流程），它属于 SSH；一个网页按钮不该承担 |
| — | 备份历史 / 备份成功率的图表 | 无需求 |

**「立即备份一次」的失败要显眼**（`#25` §6 的统一原则）：`runBackup()` **任何失败都返回 `ok:false`、绝不抛**，
所以 UI 必须**看 `ok`**，并在 `ok:false` 时用 `notice-bad` 把 `note` 原文显示出来。
⚠ 特别不能把「`note` 里有内容」当成成功信号——成功时的 `note` 也常有内容
（`backup.ts:157-163` 会在里面塞「清理了 N 份旧备份」）。

**并发点击**：【默认】用**一个进程内的布尔量**挡住重入（`backupRunning`），
第二次点击直接返回 `?notice=backup-skipped`。
为什么不更安全一点：`runBackup()` 会写 `.tmp` 再改名，同时跑两次的结果是「一个成功、另一个搬同一个库」，
**不会损坏已有产物**；加一把真正的锁（文件锁 / DB 行锁）换来的正确性提升，
抵不过它引入的失败模式。**这条与 `#25` §7 的幂等表是同一条判断的两面**。

## 6. 连带影响（落地时必须一起改）

1. **`src/server.ts:37` 的 `const site = {...}` 是模块加载时求值的、被 6 个路由共享**。
   设置进库后它必须变成**每请求解析**（`siteOf()`）：标题在管理台改完，**下一次请求就要看到新值**，
   否则「保存成功但页面没变」又成了一次静默失败。
2. **`statusPage()` 的 `probeIntervalSeconds`** 来自 `buildSummary()`（`server.ts:55`），
   改成读库（§4 末段）。
3. **`assertSessionSecret()`（`config.ts:218`）是「拒绝启动」家族的现有成员**，
   `#25` 的 `SITE_ORIGIN` 是第二个。**本票不新增第三个**——标题/描述/间隔都不是「不配就起不来」的东西，
   它们有代码默认值。
4. **`.env.example` 要改注释**（不是删行）：`SITE_TITLE` / `SITE_DESCRIPTION` /
   `PROBE_INTERVAL_SECONDS` 三行标注「**只作为首次启动的初始值**，之后真源是数据库（管理台 → 站点设置）」。
   保留这三行而不是删掉：全新部署时它们仍然有用（先灌一批初值），与 `#26` §2 对
   `TARGETS_PATH` 的处理**完全一致**。
5. **`README.md`** 要加一句「设置在哪改」的话，否则读者会先去翻 `.env`。

而不是留成模糊的期望。

**⚠ 已在本机跑过的验证**：**没有**。本票产出时的会话里 `ops_bash`（缺 bash IPC 兼容收据）与
`pwsh`（执行策略禁止 `prepare-workspace.ps1`）都不可用，上面 16 条**一条都没跑**。
**待验证的断言清单，不是已验证的结论**。

### 8.3 落地结果（2026-10-18 由 [实现⑤站点设置进库](https://github.com/Lkyloveaw/lkyloveaw-home/issues/42) 回填）

**16 条全部跑成绿**（不再是「待验证」）：

- 8.1 的 7 条 → `scripts/unit-check.mjs` 的 `[settings: 首次落值 / DB 优先 / 坏值回退]` 一节
  （每个场景在**子进程**里跑，自带 `DATABASE_PATH` / 三个 env；「再启动一次」用另一次子进程模拟）。
- 8.2 的 8–12、16 条 → `scripts/e2e-check.mjs` 的 `[站点设置进库（#42）]` 一节。
  第 12 条把「不打断正在等的那一轮」写成了断言：**保存后不会出现一次额外的立刻探测**，
  且从某一轮起间隔真的变长（用**改动前实测的间隔基线**当参照，不写死阈值 —— 观测到的
  「两轮之间的间隔」= 探测间隔 + 本轮耗时）。

- `unit-check` 207 → **238**，`e2e` 337 → **363**，`npm run verify` 全绿。

**落地时踩到的一个真坑（本文没写清，实现里已按下面的语义定死）**：
**「值坏没坏」与「值守不守表单区间」是两件事。** 一开始读路径也拿 §3 的 5–86400 判，
结果 `PROBE_INTERVAL_SECONDS=3` 的部署**升级后被静默改成每 60 秒探一次**
（实测：整个 e2e 的探测节奏被它打乱、面板曲线全空 —— 正是本仓最防的那种静默行为变更）。
最终语义：

| 判据 | 用在哪 | 规则 |
| --- | --- | --- |
| **坏没坏**（`isReadable`） | 读路径 | 空标题 / 非正整数才回退默认 + `console.error`；**低于表单下界的值照用** |
| **守不守区间**（`spec.min/max`） | 写路径 | 5–86400，越界 400 |
| **不改就不拦** | 写路径的例外 | 提交值**与库里当前值一字不差**时放行 —— 否则用户只想改标题，也会被「间隔 5–86400」拦下 |

页面上因此多一行提示：值超出表单区间时标出「它来自 `.env` 的首次落值，仍按它探测；想改就必须落回区间内」。
README 与 `.env.example` 也照这条写。

**另一处落地补充（§7 落点表没列，但必须做）**：`src/auth.ts` 的 `KNOWN_PAGES` 要加上
`/admin/settings`（以及 #40 落地的 `/admin/targets`）。不登记的表现是
**未登录点进 `/admin/settings` → 登录后被丢回首页**（`next` 校验不认这个落点）。
剩下的账号页 / 备份页由各自的票在自己落地时补。

### 8.4 备份半的落地结果（2026-10-18 由 [实现⑥备份页与手动备份一次](https://github.com/Lkyloveaw/lkyloveaw-home/issues/43) 回填）

- 第 13 条（写后读）：点一次 → 302 + `backup-started`，**磁盘上真的多一个产物**（大小 > 0）、
  页面列表里带大小与时间 —— 不是只在页面上说成功。
- 第 14 条（跳过）：再点 → 302 + `backup-skipped`，**产物一个不增**。⚠ 这一条正是 §5 里那个坑：

  只做前者会把跳过说成「又备份了一次」，只做后者会把「清理了 N 份」也当成失败。
  另外补了一条并发断言：三连点 → 产物仍只多一个（进程内布尔守卫 + 同一天只留一份，两层都兜住）。
- 第 15 条（目录不可写 → 屏幕上看得见）：失败时 `lastBackupError` 留在页面上（`notice-bad` + 原因原文），
  进程内记忆、重启即清空 —— 它不是审计，只是不让用户对着「备份失败」四个字猜。
- `unit-check` 238 → **245**、`e2e` 363 → **387**。

**一处实现层面的补充（本文 §5 没说，但页面必须能分开说）**：备份目录有**三态**，一个「空列表」糊不住：
`missing`（还没建 —— 正常，第一次备份时创建）/ 可读（可能是空的）/ `unreadable`（故障，要显红）。
实测 Windows 上「上一级是个文件」也报 `ENOENT`（不是 `ENOTDIR`），所以判定要**往上走一遍祖先链**，
否则页面会把一个配置故障说成「第一次备份时会创建」。三种状态各有断言。

已经**写在备份页上**（不是留在文档里），并且顺带写明「下载 / 恢复不在网页上，属 SSH」。
