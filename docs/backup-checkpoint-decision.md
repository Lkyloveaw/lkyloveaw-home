本文件是「备份与 checkpoint」这张票的产出。
回答六个问题：**checkpoint 时机**、**用哪个模式**、**备份怎么保证一致性**、**恢复步骤**、**Docker 属主**、**滚动备份**。

## 0. 复现票里的陷阱（本票又跑了一遍，结论一致且更细）

造一个 WAL 库（10000 行、主库 4096 B、WAL 238992 B），三条路对比：

| 路 | 产物 | 打开后 |
| --- | --- | --- |
| **只拷 `.sqlite`** | 4096 B | ★ **`no such table: probes`** |
| **连 `-wal` 一起拷** | 4096 B + WAL | 读到 10000 行（**但只有停服才安全**） |
| **`db.backup()`** | **208896 B** | ★ 读到 **10000 行**，耗时 **6ms** |

---

## 1. 备份怎么保证一致性：用 `db.backup()`，**不用 `cp`**

### 1.1 `db.backup()` 确实存在（已核实）

`better-sqlite3@13.0.3`（本仓库实际安装版本）的 `Database` 实例上有 `backup(filename, options)`，是 **async**，内部用 SQLite 的**在线备份 API**。选项：`attached`（默认 `'main'`）、`progress` 回调；目录不存在会抛 `TypeError`。

### 1.2 实测它的三个关键性质

1. **产物自包含**：208896 B，`probes` 表在、行数与源库一致。**这正是「只拷 .sqlite」办不到的事。**
2. **不会改动源库的 WAL**：打备份前后 `WAL 32992 → 32992`、主库 `253952 → 253952`。→ **备份操作本身不会替我们 checkpoint**，所以 §2 的 checkpoint 策略不能靠备份顺带完成。
3. **够快**：10000 行 → **6ms**。在这个数据量级（分钟级写入、保留 30 天、几十个目标）完全可以每天甚至每小时跑一次。

### 1.3 为什么是这三条路里唯一该选的

- **只拷 `.sqlite`** → 明确产生空库，就是本票要修的东西。
- **拷 `.sqlite` + `-wal` + `-shm`** → 能读出全量，但它是**文件系统层面的快照**：拷的瞬间 WAL 正在被写，就得到撕裂的组合。**只有停服才安全**，而这是个常驻服务。
- **`db.backup()`** → 走 SQLite 自己的读事务，**不需要停服**，产物天然一致。

**决定：备份只用 `db.backup()`。** 文档里要把「不要 `cp`」写成一条硬规矩，并说明为什么（不是「不够优雅」，而是**会静默地产生一个空库，直到你真需要它时才发现**）。

## 2. checkpoint：触发时机与模式

### 2.1 ⚠ 实测发现：`checkpoint` 会**静默失败**，所以时机不能只看时钟

这是本票最重要的一条。在**另一个连接持有读事务**时触发 checkpoint（完全正常的并发场景）：

```
插入后：主库 4096  WAL 135992
  PASSIVE   pragma 返回 [{"busy":0,"log":33,"checkpointed":2}]  → 主库 4096  WAL 135992
  FULL      pragma 返回 [{"busy":1,"log":33,"checkpointed":2}]  → 主库 4096 WAL 135992
  TRUNCATE  pragma 返回 [{"busy":1,"log":33,"checkpointed":2}]  → 主库 4096 WAL 135992
释放读事务后再 checkpoint(FULL)：主库 126976  WAL 135992
                                TRUNCATE 后：主库 126976  WAL 0
```

**模式**：

| 模式 | 语义 | 实测表现 |
| --- | --- | --- |
| `PASSIVE` | 尽量搬，**不等待**读者 | 被挡住时只搬了 2/33 页，**且返回 `busy:0`（骗人！）** |
| `FULL` | 等读者释放，把 WAL 搬空 | 被挡住时 `busy:1`，搬不动 |
| `TRUNCATE` | 同 FULL，且把 WAL 截断为 0 | 被挡住时 `busy:1`；能跑时把 WAL 归 0 |

**结论：`PASSIVE` 的返回值不可作依据**——它报 `busy:0` 却在并发下几乎没搬运。**必须用 `FULL` 或 `TRUNCATE` 并检查 `busy` 标志**；`busy:1` 表示本轮没成功，**不能当作已完成**。

### 2.2 决定：**与探测轮次绑定**，`TRUNCATE`，且校验返回值

- **时机**：跟探测轮次（`probe.ts`）一起跑，**按轮次计数降频**（例如每 N 轮一次，N 取到约「每小时一次」）。
  **为什么不跟每轮**：`probeIntervalMs` 默认 60s，每轮 checkpoint 意味着每分钟一次同步 IO——而 WAL 在这个写入量下根本不需要那么勤。**为什么不独立定时器**：多一个定时器就多一条生命周期路径（启动/停止/异常），而探测轮次本来就是这个进程唯一的心跳。
- **模式**：`TRUNCATE`。
  **为什么不 `PASSIVE`**：实测它在并发下几乎不搬运**且返回骗人的 `busy:0`**——正是「静默降级」，与本仓库的取舍相反。
  **为什么不是 `FULL`**：`FULL` 已经把 WAL 内容搬进主库，但**不截断 WAL 文件**；`TRUNCATE` 多做的这一步正好是「只拷 `.sqlite`」能成功的前提。两者成本差别在本数据量下可忽略（实测主库 4096 → 253952 是毫秒级）。
- **必须检查 `busy`**：拿 `pragma('wal_checkpoint(TRUNCATE)')` 的返回，`busy !== 0` 时**记一条日志**（说明本轮没搬完，下轮再来），**不要**当成成功。这就是本仓库「失败要显眼」的落点。

### 2.3 顺带一提：它不改行为，只改落盘时机

checkpoint 不影响 `store.ts` 的任何查询语义（读走 WAL 快照）。所以 §2.2 是个纯运维收益的改动，**零功能风险**。

## 3. 恢复步骤（**必须写成可照做的清单**）

这是本票最容易被写成「放回文件即可」而害人的部分。恢复的**危险步骤是第一步**：

1. **停服务**（`docker compose stop`，或前台 Ctrl-C）。**不停服恢复 = 一边被覆盖一边读**。
2. **确认备份文件是自包含的**（在拷回去之前先验，别把坏备份盖到好库上）：
   ```
   node -e "const D=require('better-sqlite3');const d=new D('<备份文件>',{readonly:true});console.log(d.prepare('SELECT COUNT(*) c FROM probes').get());d.close()"
   ```
   **能打出 `{ c: <非零> }` 才继续。** 打出 `no such table: probes` 说明这个备份是「只拷 .sqlite」得来的空库——**宁可现在发现**。
3. **移走现场**（不要删，改名留证）：
   ```
   mv data/availability.sqlite data/availability.sqlite.bak
   ```
   **⚠ 必须同时处理残留的 `-wal` / `-shm`**：把旧的 `availability.sqlite-wal`、`availability.sqlite-shm` **一起移走或删掉**。留着旧 WAL 与新的主库配对，SQLite 会尝试把**不匹配的 WAL** 应用到主库上——这是恢复失败最常见的原因。
4. **放入备份**：`cp <备份文件> data/availability.sqlite`，并确认目录里**没有** `-wal`/`-shm`。
5. **起服务**，看首页/面板数据是否在。
6. **再备份一次**并重复第 2 步的校验（证明新现场是好的）。

**⚠ Docker 场景的额外一步**：容器内的服务进程是 root，`./data` 里的文件属主可能是 root；在宿主机上直接 `cp`/`mv` 可能因权限失败。用容器执行更稳：
```
docker exec personal-wiki node dist/cli/backup.js --verify /app/data/availability.sqlite
```
（备份/校验 CLI 的落点见 §5——**必须放 `src/`**，否则不进镜像。）

## 4. `./data` 属主问题（仅当用 Docker 部署时成立）

> ⚠ **2026-10-15 更新：本节的前提「本机无 docker，只能静态推断」已被新事实部分推翻。**
> 目标部署机 `10.0.0.226` **同时有 Docker 29.5.1 与 systemd**，且**具备完整编译工具链**
> （`gcc 13.3`/`g++`/`make`/`python3`）——**裸机自建部署是可行且更贴合该机器的选择**
> （见 `docs/deploy-environment.md`）。
>
> **本节整节只在「选择 Docker 部署」时才适用。**
> **若改为裸机部署，本节问题直接不适用**：没有容器，就没有「容器内 root 写宿主 volume」这层 UID 错配——
> 服务与数据属主都是同一个 root，不存在跨 UID 问题。
> 因此**本节从「唯一无法验证的部分」降级为「一种部署方式下的条件性注意事项」**。
>
> **但这同时带来一个真实收益**：下面 §7 的 7 条回归用例里，有 3 条（恢复流程、残留 WAL、滚动保留）
> 此前只能纸上验证，**现在可以在那台真机上实跑**——包括最关键的「必须同时移走 `-wal`/`-shm`」。

**（以下为 Docker 部署下的原分析，内容不变。）**

原判据：本机无 docker，以下全部是静态推断，不得声称已验证（map Notes 已定这条规矩）。

已核对的事实：
- 服务在容器里以 **root** 运行（`Dockerfile` 没有 `USER` 指令），`docker-compose.yml` 把 `./data` 以**可写**方式挂进去（`./data:/app/data`），而 `targets.json` / `content` 是 `:ro`。
- 因此**容器写出来的** `availability.sqlite`、`-wal`、`-shm` 以及**备份产物**，在宿主机上属主是 root（Linux 上典型是 `root:root`）。
- **宿主用户不是 root 时**：读备份可能可以（取决于 umask/权限位），**删除或覆盖**一般不行。

**给出的可执行检查（不是「注意一下」，是能跑的命令）**：
```bash
docker compose exec site id                       # 确认容器内是 root
docker compose exec site ls -ln /app/data         # 看属主/权限位（-n 显示数字 UID）
ls -ln data/                                      # 宿主机上的同一批文件
```
两边 UID 一致 → 宿主机能直接操作；不一致 → **用容器执行备份与校验**（`docker exec`），或 `docker compose run --rm -u $(id -u):$(id -g) site ...`。

**决定**：备份脚本默认**写在数据目录旁边**（同一 volume），并**在文档里给出上面这组检查命令**；不预设宿主 UID、不加 `chown` 逻辑（那需要宿主机上下文，容器里猜不准）。

**状态修正（2026-10-15）**：本条原写「本票唯一无法在本机验证的部分，必须标成未验证」。
现已知目标部署机存在（`10.0.0.226`，有 Docker 也有完整工具链），故：
**若走 Docker 部署** → 这组命令**可以直接在那台机上真跑**，未验证状态可解除（跑之前仍不得声称已验证）；
**若走裸机部署** → 本节不适用，连「未验证」都不必挂。见 `docs/deploy-environment.md`。

## 5. 滚动备份

**决定：做，**保留最近 7 份**，按日期命名，备份前先「够用就跳过」。

- **命名**：`availability-YYYY-MM-DD.sqlite`（**一天一份**，同一天重跑覆盖）。用日期而不是序号，是为了让「最新的是哪份」「这份是哪天的」不需要额外元数据。
- **保留**：按文件名日期排序，**只留最近 7 份**，超出的删掉。7 天覆盖「改了配置/升了版本，第二天发现坏了」这个最现实的场景。
- **磁盘占用（已实测）**：备份产物 ≈ 主库大小（实测 10000 行 → 208896 B ≈ 204 KB）。**7 份 ≈ 1.4 MB**，相对 30 天保留策略下的库规模可忽略。→ **不需要压缩**（压缩会引入一次性解压步骤，反而增加恢复时的出错面）。
- **触发**：**跟 checkpoint 同一个引擎**（每小时一次的那个 tick），但**按「今天还没有成功备份过」判断**——这样重启/崩溃不会导致当天漏备份，也不会一天备份 24 次。
- **失败要显眼**：备份写盘失败（磁盘满、权限）必须 `console.error` 并且**不影响探测循环**（探测是主职责，备份失败不能把探测带下去）。

**⚠ 顺序**：**先 checkpoint 再备份**。虽然 `db.backup()` 本身不依赖 WAL 被搬空（实测它能读到 WAL 内容），但先 `TRUNCATE` 能让备份读到的增量更小、也让「主库文件」本身保持随时可用的状态（万一备份这条路坏了，主库至少不是个 4KB 空壳）。

| 文件 | 改动 |
| --- | --- |

## 7. 可断言的回归用例

1. **空库陷阱回归（本票的核心）**：造一个 WAL 有大量内容、主库极小的库 →
   - 断言「只拷 `.sqlite`」副本**打不开 `probes` 表**（把这个陷阱本身钉成断言，防止有人日后又改用 `cp`）；
   - 断言 `db.backup()` 的产物**表在、行数与源库一致**。
2. **checkpoint 真的搬了**：`wal_autocheckpoint=0` 造出大 WAL → 跑一轮 checkpoint(`TRUNCATE`) → 断言 WAL 归 0 **且主库变大**；断言返回的 `busy === 0`。
3. **并发下不谎报成功**：让另一连接持有读事务 → 断言 checkpoint 的返回 **`busy !== 0`**（`PASSIVE` 会返回 `busy:0` 却在并发下几乎不搬运——**这条断言是防「静默降级」的**）。
4. **恢复流程可执行**：按 §3 的清单做一遍（停服务 → 移走主库与 `-wal`/`-shm` → 放回备份 → 起服务）→ 断言面板/`/api/status` 能看到历史数据（行数不为 0）。
5. **残留 WAL 会坏事的反面**：把**旧**的 `-wal` 与**新**的主库配在一起 → 断言这是失败场景（用来证明 §3 第 3 步「必须一起移走」不是多余的）。
6. **滚动保留**：造 10 个不同日期的备份文件 → 跑清理 → 断言**只剩最近 7 份**、且留下的是**最新**的 7 个。
7. **备份失败不拖垮探测**：把备份目录设为不可写 → 断言探测循环照常跑（有 `[probe]` 日志）、备份错误**显眼地**打了出来。

## 8. 边界

- 本票**不改** SQLite 的 journal 模式（仍是 WAL，这是 map 既有取舍）。
- 本票**不做**异机/远端备份（个人站单机单 volume；要异地是另一个需求）。
- 本票**不做**备份加密或压缩（§5 已说明：容量可忽略，压缩反而增加恢复出错面）。
- 本票**不改** `Dockerfile` 的 root 运行方式——那属于 map 的 Not yet specified（「容器以 root 运行、`./data` 属主问题」），本票只提供**检查手段**与**用容器执行**的绕法。
- §4 的 Docker 部分**仅在 Docker 部署下适用**；裸机部署时该问题**不适用**（2026-10-15 修正：目标部署机 `10.0.0.226` 已存在，见 `docs/deploy-environment.md`；若走 Docker，那组检查命令可在那台机上真跑）。
