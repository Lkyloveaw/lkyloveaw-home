## 0. 结论速览

| 问题 | 结论 |
| --- | --- |
| `targets` 表结构 | `id TEXT PRIMARY KEY` + `name/url/group/expect_status/timeout_ms/enabled/enabled_at/updated_at`；`id` 是主键，历史靠它关联 |
| 首次导入怎么认 | **表为空就导入**（每次启动都查一遍，是幂等的）。文件来源优先 `TARGETS_PATH`，其次 `TARGETS_JSON`，**与今天 `config.loadTargets()` 的优先级一致** |
| 文件之后还算不算真源 | **不算**。表里有行之后，**文件被完全忽略**：不做新增、不做更新，只**打一行警告** |
| `id` 能不能改 | **不能**。UI 上编辑表单里 `id` 是只读文本；要换 id = 「新增一个 + 停用旧的」 |
| 删除 = 停用 | **是**。`DELETE` 只允许在**该 id 没有任何历史**时物理删行（用来收拾打错的 id）；有历史一律 `enabled=0`。另有**显式**「删除并清空历史」（必勾确认框，§4 修订） |

| 谁还得改 | `buildSummary()` / `/healthz` / `probeAll()` / `getUptimeRaw()` / `aboutPage()` 今天都读 `config.targets`，全要换成读库 |

## 1. `targets` 表

```sql
CREATE TABLE IF NOT EXISTS targets (
  id            TEXT    PRIMARY KEY,
  name          TEXT    NOT NULL,
  url           TEXT    NOT NULL,
  grp           TEXT,
  expect_status TEXT,              -- JSON 数组，如 "[200,301]"；NULL = 用默认区间
  timeout_ms    INTEGER,           -- NULL = 用全局 PROBE_TIMEOUT_MS
  enabled       INTEGER NOT NULL DEFAULT 1,
  enabled_at    INTEGER NOT NULL,  -- 当前启用状态的起始时刻（见 §5）
  updated_at    INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_targets_enabled ON targets (enabled);
```

与 `ProbeTarget`（`src/config.ts:9-21`）的映射：`id`→`id` · `name`→`name` · `url`→`url` ·
`group`→`grp` · `expectStatus`→JSON 文本 · `timeoutMs`→`timeout_ms` · `enabled`→`enabled`（1/0）。

**为什么列名叫 `grp` 不叫 `group`**：`GROUP` 是 SQL 保留字，用它当列名在每条 SQL 里都要加引号，
而**漏加一处**的报错信息（`near "group": syntax error`）会在日常维护里反复出现。
领域词仍然是「分组」（`CONTEXT.md`），只在这一层换个拼写。

**为什么 `expect_status` 存 JSON 文本而不是另开一张表**：它最长也就是 `[200,301]` 这种几元素的数组，
拆表要引入 join 与排序，而它的实际用法就是「整取整存、只判断包含」。SQLite 的 `json` 函数可用，
但**本仓的既有取向是不为这种量级引结构**（`store.ts` 把整个探测结果压在一张表里，同一判断）。

**为什么没有外键指向 `probes`**：`probes.target_id` 是 TEXT 且历史行可能**比目标本身活得久**
（停用只置 `enabled=0`，历史一行不删）。加外键就得决定「删目标时历史怎么办」，而我们的答案是
**不删有历史的目标**（§4），所以外键挡不住任何真实情形，只会让迁移多一个失败模式。

## 2. 首次导入：什么时候算「首次」

```
启动顺序：
  initStore() → initUsers() → initTargets()
  initTargets():
     SELECT COUNT(*) FROM targets
       = 0  → 从文件/环境变量读一次清单 → 校验 → 在一个事务里全部插入 → 打日志（导入了 N 条）
       > 0  → 什么都不做
                若同时发现「文件存在且内容非空」→ console.warn：文件已被忽略，真源是数据库
```

**为什么判据是「表为空」而不是「一个持久化的标志位」**：标志位要额外存一处状态，而它自己也会被
「恢复了一份旧备份」「手工改库」搞坏。`COUNT(*) = 0` 是**从数据本身推出来的**，不需要额外真相。
代价：把表清空后再启动会**再导入一次**文件——但那恰好是「用户把目标删光了、想回到文件」的合理期望。

**幂等性**：导入整段包在一个 `db.transaction` 里，用 `INSERT OR IGNORE`。
所以「导到一半崩溃」不会留下半张表：要么全进，要么全不进。重复执行（比如并发启动两个进程）
第二条 INSERT 被主键挡掉，不会出现重复行。

**导入的校验复用既有函数**（不改一份）：`config.normalizeTargets()`（`src/config.ts:125`）已经负责
「跳过缺 id/name/url 的条目、`validateTargetUrl()` 拦协议与 URL 凭证、跳过重复 id」，
并且**每跳一条都打 `console.warn`**。导入时直接调它，于是「文件里被拒的 URL」在库里也不存在。

**【默认】文件之后被完全忽略，而不是「文件里新增的条目自动补进来」**

| 选项 | 后果 |
| --- | --- |
| **完全忽略（选它）** | 行为教得会：「换了网页之后，`targets.json` 就退休了」。破坏性为零——它永远不会覆盖你在网页上改过的东西 |
| 文件里的新 id 自动插入 | 看起来方便，但它意味着**每次启动都在猜**「这条是新增还是我刚在网页上删掉的」。用户删掉一个目标后重启，它**自己长回来** |
| 文件覆盖数据库 | 最坏：网页上改一次、重启就没了 |

那行警告是这条选择的配套：**静默忽略**才是最难排查的形状（用户改了文件、重启、
发现「没生效也没报错」）。警告文案要说清三件事：文件被忽略、真源是数据库、要改就去管理台。

**【默认】`TARGETS_PATH` / `TARGETS_JSON` 保留但降级为「首次导入的来源」，并在 `.env.example` 与
`aboutPage()` 里写明「只用于首次导入」**。不删它们：删了会让「全新部署、想一次灌一批目标」
的人只剩网页一条路（而那时管理台刚建好、账号也刚建）。

## 3. `id` 不可变

**结论：`id` 是 `targets` 的主键，一旦创建不可修改。**

- **UI**：编辑表单里 `id` 是**只读文本**（不是禁用输入框——禁用控件在提交时没有值，
  而我们需要它作为 `WHERE id = ?` 的依据；用只读文本 + 隐藏字段，或直接用 URL 里的 id 定位）。
- **服务端**：编辑动作的 `action` 里**没有**「改 id」这一个（`#25` §5.3 的 action 是闭集，
  没有的动作就是 400）。
- **要换 id 怎么办**：在管理台**新增**一个用新 id 的目标，再把旧 id 的目标**停用**。
  这是两步显式动作，而不是一次「重命名」。

**为什么不做「允许改 id，但警告会丢历史」**（票面给的另一个选项）：
「警告 + 允许」把代价压在一次点击上，而它丢的是**不可再生的**东西——
`probes.target_id` 是历史库的关联键（`CONTEXT.md` 的目标词条、`config.ts:8` 的注释都点过这一处），
改 id 之后旧行全部成为孤儿。用一个「知道了」的复选框承接不可逆的数据丢失，是这个界面里
**唯一**不设前提的破坏性动作，与 `#23` §5 立的那条判据（*屏幕外有人立刻受影响* / *靠另一条通道才能恢复*）
正好相反：它既影响屏幕外（历史归属），又没有恢复通道。

> **那为什么不干脆「改 id 时顺带把 `probes.target_id` 一起 UPDATE」**：技术上可行，但那是在
> **改写历史**——旧探测记录的归属会被悄悄改成另一个名字。id 的作用就是「不可变的身份」；
> 可变的那一栏叫 `name`，它**已经存在**了。真需要「同一个系统换个标识」，语义上是
> 「新建一条 + 停用旧的」，正与 §4 的删除语义一致。

## 4. 删除 = 停用；只有当**没有历史**时才允许物理删

**【默认】** 这条是对 map Notes 第 3 条（「删除 = 停用（保留历史）」）的**精确化**，不是推翻：

```sql
-- 「删除」动作在服务端分两岔，由历史行数决定：
SELECT COUNT(*) FROM probes WHERE target_id = ?
  = 0  → DELETE FROM targets WHERE id = ?          -- 物理删：收拾打错的 id
  > 0  → UPDATE targets SET enabled = 0, updated_at = ?   -- 停用：保留历史
```

**为什么加这个分岔**：只有「停用」的话，一个 id 打错的目标会**永久占据那个 id**
（`name` 可以改，`id` 不能改，§3），而它没有任何历史——这正是「无代价却不可挽回」的形状。
反过来，有历史时物理删除会留下孤儿行（`probes` 里一堆指向不存在目标的记录，
`getUptimeRaw()` 的「参与目标数」也会因此对不上）。

**判据是「有没有东西可丢」，所以这条规则没有任何需要用户判断的地方**：
没历史 = 丢了也没损失，删；有历史 = 删了就丢东西，停用。
UI 上的措辞跟着走：「删除」（无历史时）与「停用」（有历史时），**不是**一个按钮两种命运——
按钮文案由服务端按同一判据渲染，用户看到的就是会发生的那件事。

**停用的状态语义**：`enabled=0` 的目标不再被探测（`probeAll()` 过滤），
**从首页/面板的列表里消失**（与今天 `buildSummary()` 的 `filter(t => t.enabled !== false)` 一致），
但**历史仍在库里**：`getRecentIncidents()` 按 `at` 查全表，所以「近期异常」里
可能仍出现一个已停用目标的名字——那是**正确的**（它确实异常过），
`statusPage` 的既有代码已经用 `summary.targets.find(...)` 做了「找不到就显示 id」的兜底
（`views.ts:394`），所以不会崩，只是显示成 id。

**【默认】不做「彻底删除（含历史）」**：那是一次不可逆的批量删数据，而它的价值只是
「清理一个我不想要的历史」。要终止历史增长，停用就够了（不再产生新行）；
真要清历史，CLI 或 SQL 是更合适的位置——一个网页按钮不该承担这个。

> 🔁 **2026-10-23 修订（用户明确要求）**：上面这条被推翻。管理台新增一个**显式动作**
> 「删除并清空历史」（`action=target-purge`）：在**同一个事务**里
> `DELETE FROM probes WHERE target_id = ?` 再 `DELETE FROM targets WHERE id = ?`。
> 它必须勾**必勾的确认框**（`name=confirm`），服务端独立校验，与「重置口令」同一档。
>
> 为什么改：`targets.json` 灌进来的**演示目标**带着几千条假历史（`example.com` 的 200），
> 留着会污染真实系统的曲线；而「停用 + 等 `PROBE_RETENTION_DAYS` 把历史自然清掉」
> 对一次性清理太绕。默认的「删除 = 停用」**不变**——这个动作只出现在**有历史**的行上，
> 且是唯一的逃生口。代价是承认了「一个网页按钮可以删历史」；补偿是确认框写清后果、
> 服务端独立校验、并且不与普通「删除」共用入口（`purgeTarget()` 只由 `target-purge` 调用）。

> 同日回归补强：物理删除后，本进程已发出的旧探测请求不得重新写回历史。目标模块记录物理删除代际，探测轮次在写入前剔除失效快照；删除后复用同一 id 也不会混入旧结果。普通停用不失效当前轮次，仍按下一轮生效。真实本机 HTTP 门闩用例覆盖清空、清空后复用 id、无历史物理删除，并保留同轮正常目标作对照（`scripts/probe-purge-check.mjs`）。该代际约束依赖 ADR 0001 的单进程部署；若改成多进程探测，需要改用数据库中的实例标识。

**停用后再启用**：允许（`#24` §3 把「启用」定为永不设卡的恢复通道，同一条精神）。
`enabled_at` 因此要跟着变（见 §5）。

## 5. `enabled_at` 这个列是干什么的（`upStreakMs` 的一个真实坑）

`getStats()` 会算「连续可用时长」（`store.ts:270-290`）：从最近一次**非 up** 记录之后的第一条 up 算起。

今天这个算法对「停用再启用」有一个**静默撒谎**的分支：目标停用两个月（这段时间没有探测记录，
自然也没有「非 up」记录），重新启用后第一轮探测是 up → 于是连续可用时长会从**两个月前**开始算，
界面上显示「连续可用 60 天」——而它其实停用了 60 天。

**处置**：`targets.enabled_at` 记「当前启用状态的起始时刻」，
`getStats()` 的窗口下界取 `max(窗口起点, enabled_at)`；停用再启用后 `enabled_at` 刷新为当前时刻。
这样「重新启用」之后的连续可用从**重新启用那一刻**算起，说的是实话。

> **为什么值得为这个加一列**：`store.ts:268-269` 的注释已经写明这个仓库的立场——
> 「可用性承诺（"连续稳定 3 天"）必须经得起回看，近似值会撒谎」。
> 「停用两个月后显示连续可用 60 天」正是它点名要防的那类谎，而它由本次改动**新引入**
> （今天停用是改文件+重启，用户不会把它当成「运行中」；搬进网页后停/启变成日常动作）。

## 6. 探测轮次怎么拿到最新清单

**【默认】每一轮开头读一次库，不做缓存、不设版本号。**

```ts
// probeAll() 的第一行，替换今天的 config.targets
const targets = listEnabledTargets()   // SELECT ... WHERE enabled = 1 → ProbeTarget[]
```

**为什么不做「缓存 + 版本号」**：探测间隔默认 60 秒，一天 1440 次单表 SELECT，
而 SQLite 的这类查询是**微秒级**（`docs/session-decision.md` §7.5 对「每请求一次主键 SELECT」
给过同一个判断：「个人站数据量毫秒级，不加缓存层」）。缓存要引入一个版本号、
一个失效路径、以及「版本号没更新 → 网页上刚加的目标不生效」这个**新的静默失败**。
用一次微秒级查询换掉一整套失效逻辑，这笔账不需要犹豫。

**生效时机**：网页上改完 → **下一次探测轮次**开始生效（≤ 1 个间隔，默认 ≤60 秒）。
这与「#22 的探测间隔立刻生效」是同一条纪律的两个实例：**都不打断正在等的那一轮**。

**`probeAll()` 一轮只读一次**（循环外），所以一轮之内不会出现「前半轮有它、后半轮没有它」。
`roundAt` 依然是一轮一个（`store.ts:20` 的既有约束：整体可用率必须按轮聚合）。

### 6.1 并发写与探测读：事务边界

| 方向 | 处置 |
| --- | --- |
| 探测读 ← 网页写 | **不需要事务**。一轮开头读完就与后续写无关；WAL 模式下读不阻塞写（`store.ts:56` 已开 WAL） |
| 网页写 → 网页写 | 单进程 + SQLite 串行，`better-sqlite3` 是同步 API，**天然没有交叉**（不存在两个写事务交错） |
| 「新增」与「删除」抢同一个 id | 靠**主键唯一约束 + 捕获 `SQLITE_CONSTRAINT_PRIMARYKEY`** 兜底，把它翻成一句人话（「id 已存在」）。不用「先查再插」——那是 TOCTOU 的形状，虽然本进程串行使它今天不会触发，但依赖「今天不会并发」是脆的 |
| 「删除」的两岔判定 | `COUNT(*)` 与随后的 `DELETE`/`UPDATE` **必须在同一个 `db.transaction` 里**，否则「查的时候没历史、删的时候已经有了一行探测记录」就漏了 |

## 7. 连带影响（落地时必须一起改，否则验收是假的）

今天读 `config.targets` 的地方**每一处**都要换（已 grep 核实，共 5 处）：

| 位置 | 今天 | 之后 |
| --- | --- | --- |
| `probe.ts:80` `probeAll()` | `config.targets.filter(...)` | `listEnabledTargets()` |
| `server.ts:41` `buildSummary()` | `config.targets.filter(...)` | `listEnabledTargets()`，**每请求读一次** |
| `server.ts:263` `/healthz` | `config.targets.length` | 库里启用中的目标数（一次 SELECT COUNT） |
| `server.ts:279,281` 启动日志 | `config.targets.length` | 同 `/healthz` |
| `store.ts:404` `getUptimeRaw()` | `config.targets.filter(...).length` | 同上面同一次读的结果——**这一处最危险**（见下） |
| `views.ts:301-308` `aboutPage()` | 教用户「编辑 `targets.json`」 | 改成「在管理台 → 系统可用性 里新增」（`#23` §8.1 已登记） |

> ⚠ **`getUptimeRaw()` 是这次改动里最容易出错的点**：它拿
> `HAVING total >= 期望目标数` 过滤掉「旧库迁移来的每轮只有 1 个目标」的历史点
> （`store.ts:398-401` 的注释解释了为什么必须这么过滤）。若它读到的是**冻结的**目标数，
> 而 `buildSummary()` 已经用了**库里的**新目标数，两张图的口径就会分叉——
> 表现为「可用率曲线上少了几个点」这种没人会立刻发现的偏差。
> **处置**：同一请求内，目标清单**只读一次**，把同一个数组传给 `buildSummary()` 与 `getUptimeRaw()`。

**`config.targets` 这个字段本身怎么处置**：保留它（`config.ts:177`），但**只作为首次导入的来源**
（§2 已经要用它），不再有任何运行时读者。不删是因为 `loadTargets()` 里的
`TARGETS_JSON` / `TARGETS_PATH` 解析与 `normalizeTargets()` / `validateTargetUrl()` 都还要用，
删它等于把导入路径一起拆了。

### 9.1 库与导入（`scripts/unit-check.mjs`，可用临时库直跑）

| 11 | 目标停用 2 分钟后重新启用 | 触发一次 up | `upStreakMs` **从重新启用时刻起算**，不是从停用前（§5 的坑） |

### 9.3 落地结果（2026-10-18 由 [实现④目标网页化](https://github.com/Lkyloveaw/lkyloveaw-home/issues/40) 回填）

**上面 18 条全部跑成绿**，不是「待验证」了。断言位置：

- 9.1 的 12 条 → `scripts/unit-check.mjs` 的 `[targets: 首次导入 / id 不可变 / 删除两岔 / enabled_at]`
  一节（全部在**子进程**里跑：每场景自带 `DATABASE_PATH` / `TARGETS_JSON`，互不污染）。
  其中第 12 条是**真并发**四个子进程打同一个新库。
- 9.2 的 6 条 → `scripts/e2e-check.mjs` 的 `[管理台目标写路径（#40）]` 一节。
  第 14 条（热加载）用「新目标的 `timeline` 有没有记录」证明 —— 那只能来自探测真的跑了它；
  第 18 条是文本断言（`src/` 里除 `config.ts` 与 `targets-store.ts` 外不许出现 `config.targets`）。

**落地时发现并修掉的既有缺陷**（第 12 条逼出来的）：两进程同时首启会**崩在补列迁移上** ——
「读 `PRAGMA table_info` → 缺列就 `ALTER TABLE`」这个形状在并发下必有一个进程拿到
`duplicate column name`，进程退出 1、服务起不来。实测负载下 100 次并发首启里必现 1 次。
`store.ts` 的 `probes.round_at` 与 `users.ts` 的 `token_version` / `role` 三处同一形状，已全部改成幂等
（新增 `isDuplicateColumnError()`：只容忍这一种措辞，别的错照抛）；修后同一压测 100 次 0 失败。
`users.ts` 那处还顺带绑住了「补列」与「一次性全表提权」，避免并发下把新号一起提权。

**两处与本文原定的偏差（记录事实，不偷偷改）**：

1. **§2 的优先级那句话内部矛盾**：原文写「文件来源优先 `TARGETS_PATH`，其次 `TARGETS_JSON`，
   与今天 `config.loadTargets()` 的优先级一致」，但 `loadTargets()` 实际是 **`TARGETS_JSON` 优先**。
   落地按**「与今天一致」**那一半做（`TARGETS_JSON` 优先），因为改导入优先级不在本票范围内。
2. **首次导入会让「连续可用时长」从导入那一刻重新起算**（`enabled_at` = 导入时刻）。
   对全新部署没有差别；对**升级上来的库**，历史一行没丢，只是「这一段连续」从迁移起算。
   这是 §5 那条规则的一次性代价，方向是保守的（少报而不是多报）—— 真机验收（票⑩）会看到它。


**⚠ 本票产出时**：会话里没有可用的命令通道，18 条**一条都没跑** —— 那是当时的事实，
不是现在的状态。**落地结果见下面 §9.3**（全部跑成绿，并逼出了一个真 bug）。

## 10. 边界

- **不定**站点设置的真源（[#22](https://github.com/Lkyloveaw/lkyloveaw-home/issues/22) 处理标题 / 描述 / 探测间隔）。
  本文只碰「目标清单」这一件事。
- **不定**写路径的鉴权与 CSRF（[#25](https://github.com/Lkyloveaw/lkyloveaw-home/issues/25) 已定）；
  本文假定写路由已经过 `requireAdmin` + L2 + L3。
- **不定**管理台的目标页长什么样（[#23](https://github.com/Lkyloveaw/lkyloveaw-home/issues/23) §6.2 已定）：
  按 `group` 分标题、行内编辑、`id` 只读、停用旁写后果说明。
- **不做**「彻底删除（含历史）」（§4）· **不做**目标的排序 / 拖拽 / 标签体系（无需求）·
  **不做**「按文件同步」（§2 已否）· **不做**目标清单的版本号 / 变更审计（审计仍是 map 迷雾）。
- **不做**探测引擎本身的改造（并发、重试、告警）——那是 map 的 Out of scope。
- 本文产出决定与落点，**不写实现代码**。
