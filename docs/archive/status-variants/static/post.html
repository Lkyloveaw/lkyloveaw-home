把个人站搬到内网：登录闸门是怎么加上的

2026-10-16 ·约 6 分钟 · 运维 网络

这个站原本是「谁在网里谁就能看」。把它关起来的过程里，真正难的不是写钩子，而是接受一个反直觉的事实：要「默认拒绝」，就得先把所有该放行的东西一件件列出来。

一个钩子覆盖全站，但静态资源也得进白名单

起初我以为静态资源不走业务钩子。实测推翻了这个假设：全局 onRequest 会拦到 @fastify/static 提供的文件，而且与注册顺序无关。

后果很直接：如果把白名单写成一个前缀匹配，登录页自己就拿不到 /style.css，渲染成一张裸 HTML。所以白名单是精确路径匹配，每个静态资源显式列出。

默认拒绝、白名单显式放行——失败安全的形状，代价是每加一个静态文件都要记得登记一次。

未登录的响应有两种，不能一律 302

判据是「请求要的是 HTML 还是 JSON」，而不是路径前缀。原因是面板用 fetch 拉数据：

fetch('/api/status', { headers: { accept: 'application/json' } })
  .then(r => r.json())

如果这里回 302，fetch 会默认跟随跳转，拿到登录页的 HTML，r.json() 直接抛错。所以页面回 302、API 回 401。

三条实测出来的地雷

  1. 畸形 cookie 会打成 500：timingSafeEqual 对不等长输入会抛 ERR_CRYPTO_TIMING_SAFE_EQUAL_LENGTH。必须先比 byte length，不等直接判失败。
  2. 载荷形状校验不能省：exp 若不是数字，now < NaN 恒为 false，看起来像「永久有效」——一个静默的安全洞。
  3. 回跳值能逃出站外：//evil.com、/\evil.com、\/evil.com、https://evil.com 都会逃。所以要解析后比对 origin，并且落点必须在已知路由内。

一张表，把上面这些定死

输入情形结果
签名正确、未过期、版本一致、账号启用ok
now >= expexpired
改了载荷但签名没换bad-signature
签名长度不对bad-signature（不抛 500）
账号被停用disabled

这类判定表的价值不在「测过了」，而在于它能不过 HTTP 直接断言——纯函数，不需要起服务、不需要造 cookie。

还是有一件事没法只靠签名 cookie 做

登出。签名的 cookie 是无状态的，服务端无从知道一份被复制走的 token 存在。所以「登出」只能让当前这台浏览器忘掉它。真正的吊销得靠另一条通道（改口令，或者建一张会话表）。

这一点后来专门开了一张票来改——但那是另一个故事了。
