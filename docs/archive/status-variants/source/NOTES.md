> 定稿后：选中的变体**重写**进 `src/views.ts`（不是搬过去——原型是在无测试、无错误处理的约束下写的），

## 一条命令

```bash
npm run prototype
```

然后打开 **<http://localhost:3000/status?variant=A>**（`A` → `B` → `C`）。
门禁（登录闸门）仍然生效——第一次会让你登录；零账号时按提示用 CLI 建号。

- 不带 `?variant=` 时看到的是**现有生产 UI**，可以用来对照。
- 底部黑药丸是变体切换条：左右箭头点，或按 **←/→** 键。**它不是设计的一部分。**
- 页面本身的导航、数据、鉴权都是真的（技能要求的 sub-shape A：挂**已存在**的路由，只换渲染子树）。

## 三个变体在争什么

它们不是三种配色，是三种**信息层级 + 主操作**：

| | 变体 | 一句话 | 主操作 | 什么时候它更好 |
| --- | --- | --- | --- | --- |
| `A` | **值守台** | 故障占满版面，健康折叠成一行 | **扫** | 挂在常驻标签页/大屏；只想立刻知道「现在什么坏了」 |
| `B` | **卡片墙 · 时间格** | 每个系统一张卡，卡里铺一条**定宽时间格带** | **比** | 想横向比较（谁在什么时候坏过、谁 P95 差、谁连续稳定久） |
| `C` | **时间轴优先** | 所有目标的行连成一片共享时间轴 | **定位** | 排查「昨晚那段时间到底怎么了」 |

三者的**信息层级明显不同**：A 把「故障名单」当第一等公民、健康只配一行字；
B 让每个目标自洽（格带 + 徽标 + 延迟曲线 + 键值），代价是扫「什么坏了」要多看几个卡；
C 把时间当第一轴、目标是行，代价是单目标的细节被压扁。

### B 是 A/B 融合后的产物（用户反馈：「B 的可用率换成 C 的格子连成一片」）

第一版 B 的每张卡顶部是一个**可用率环**（内联 SVG 圆环）。用户看过后要求换成 C 的格子带：

| | 融合前 | 融合后 |
| --- | --- | --- |
| 卡顶部主视觉 | 可用率环（一个百分比） | **56 格定宽时间格带**（旧 → 新） |
| 能看出「什么时候坏的」 | ❌ 环只有一个总数 | ✅ 逐格看得出哪几次掉下去 |
| 卡与卡能横向比 | 环大小一致，可比 | 格带**宽度与格数完全一致**，比的是图案 |
| 百分比去哪了 | 环的圆心 | 格带下面那行小字（`可用率 99.82%`） |

两个实现要点（都不是随意定的）：

1. **格数固定 56，不是按实际点数渲染**。否则刚建库时只有 2 次探测 → 格带缩成一个小条，
   看起来像布局坏了，而且**各卡长度不一就没法横向比**。
2. **缺的格画成空心格**（`.is-none` 的内描边方框），不是留白、也不是假装 up ——
   库里确实没有那段时间的记录，画成任何状态都是撒谎。所以新库上看是「左 48 格空心 + 右 8 格实心」，
   随着探测推进，空心格会一格一格被填满。

A 与 C **保持原样**，这样你还能对照「共享长条（C）vs 卡内格带（B）」哪个更好用 ——
如果 B 赢了，C 可以直接删掉；如果发现「对齐的长条」才是你真正想要的，那说明赢家其实是 C 的骨架。

## 代码在哪

| 文件 | 是什么 |
| --- | --- |
| `src/prototype/status-variants.ts` | 三个变体 + 切换条 + 页面组装。**主内容区完全不共享代码**，每个变体自己决定布局 |
| `src/prototype/prototype-css.ts` | 原型专用 token 与样式。**只有 token，没有布局类**——避免共享 Layout 把变体拉平 |
| `scripts/prototype-dev.ts` | 开发入口：没有 `.env` 时生成**临时**会话密钥，好让「一条命令」成立 |
| `src/server.ts` 的 `/status` | 唯一的生产面改动：`?variant=` 时换渲染子树，且要求 `NODE_ENV !== 'production'` |

**为什么原型样式不复用 `public/style.css`**：那份样式正是这次要判定去留的东西，
拿它渲染候选等于用旧答案给新问题投票。

**为什么每个变体用自己一套 class**（`.va-` / `.vb-` / `.vc-`）：技能的反模式里写着
「共享 `<Header>` 可以，共享 `<Layout>` 就毁掉了原型」。共享的只有站点头栏、状态点形状、图表函数、切换条。

## 生产安全

两条闸，任一成立都不会渲染原型：

1. 路由要求 `NODE_ENV !== 'production'`；
2. 不传 `?variant=` 就走原来的 `statusPage()`。

所以即使线上有人手敲 `/status?variant=A`，拿到的也是正常的 `/status`。
`scripts/prototype-dev.ts` 只用于 `npm run prototype`，不参与 `npm run build` 的产物。

## 我需要你回答的

翻完之后，最有用的反馈通常是「**我要 B 的头部 + C 的时间轴**」这种杂交，而不是「选 B」。

1. **哪个变体赢**（或要哪几块拼起来）？
2. **A 的「健康折叠成一行」够不够**？还是要给健康目标也留一点版面（比如一行一个小方块）？
3. **C 的共享时间轴**是否真的比 B 的「每卡各自一条」更有用？如果你排查时从不看「什么时候」，C 就没价值。
4. **状态色的取值**：深色下 `#46d07d` / `#edc257` / `#ff6b5e` 够不够？**琥珀与故障红会不会太近**？
5. **顶栏 5 项**（加「管理」后）在 900px 下不换行，接受吗？

## 已知的未验证处（不假装它测过了）

- **没有跑过 `npm run typecheck`，也没有真正启动过服务看过一眼**：产出这个原型的会话里
  `ops_bash`（缺 bash IPC 兼容收据）与 `pwsh`（执行策略挡在 `prepare-workspace.ps1` 前）都不可用。
  三个变体的**类型正确性与渲染效果都是未经运行验证的**。第一次 `npm run prototype` 可能会遇到
  编译错误或布局错位——那是预期内的，请把报错贴回来。
- 图表的 CSS（`figure.chart` 的固定高度）是必需的：`charts.ts` 给 svg 加了
  `preserveAspectRatio="none"`，**没有固定高度会被垂直拉爆**。这条已在 CSS 里注明。
