# 交互动效设计

用户已体验独立原型，并于 2026-10-25 确认「可以就这样，节奏挺好的」。以这次确认的预览为设计依据，落实到现有界面。

## 意图与范围

为登录、保存和上传结果、菜单展开提供清楚而克制的反馈，沿用当前暖色、深浅色及手机布局。不增加动画依赖，不改变账号权限、业务数据或现有原生表单的降级行为。

## 采用的方案

- 原型方案：登录按钮在真实请求期间显示「正在验证…」，验证成功显示勾和「登录成功」，停留 **520ms**，登录卡片以 **220ms / 6px** 淡出，再访问服务器校验过的原目标。没有原型中模拟请求的 650ms 人为等待。
- 保存、上传及改密的公共结果提示在原位置以 **220ms / 6px** 淡入。提示持续可见；长期状态警告不播放操作结果动效。
- 账户菜单改用相同的 **220ms** 轻微位移过渡，保留当前点击、悬停、键盘和触屏逻辑。手机原生导航抽屉展开时使用同样的短过渡；收起沿用原生 `details`。
- 系统设置 `prefers-reduced-motion: reduce` 时关闭新增动画，登录成功直接导航，保留文字结果。

## 方案比较

1. 只给现有重定向加 CSS：改动最小，但登录页会在成功确认播放前被替换，无法提供已经确认过的成功反馈。
2. **采用：原生表单 + 小段渐进增强 JavaScript。** 登录请求显式要求 JSON，服务器完成原有验证及会话写入后返回安全站内路径；浏览器负责短反馈和跳转。无 JavaScript 仍为原 POST、401 HTML 和 302 回跳。
3. 额外成功中转页或动画库：会增加一次导航或依赖，对本次交互没有必要。

## 登录契约

- `POST /login` 使用现有的用户名、口令和 `next` 字段；来源校验、验证口令和签发会话保持在现有位置。
- `Accept: application/json`：成功 `200 {ok:true,next:string}`；凭据不正确 `401 {ok:false,error:"用户名或口令不正确"}`。HTML 请求保持原行为。
- 浏览器只在成功状态与结构有效、目标为同源路径时确认成功；错误、异常响应、断网和 15 秒超时显示持久的重试提示，恢复提交按钮。禁止自动再发一遍口令。
- 请求期间禁止重复提交。返回缓存页面时清理忙碌状态并取消过期回调，避免后退后突然跳页。不要记录口令或保存到浏览器存储。
- 新脚本允许匿名读取；CSS 使用一次性的版本查询参数跨过旧缓存，脚本及 CSS 后续重新验证缓存，避免新标记配旧样式。

## 实施与验证

原生 JavaScript、CSS、现有 Fastify 与现有脚本验证工具。真实 Fastify 临时库验证登录与来源、回跳及资源契约；浏览器脚本测试验证状态、失败和取消；真实浏览器检查成功/失败、结果提示、菜单、手机、深浅色和减少动态效果。原型仅作参照，重新实现正式代码，不把演示页面或假数据放入产品。
