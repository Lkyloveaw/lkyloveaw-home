# 视觉原型定稿：面板采用「卡片墙 · 时间格」

本文件是「整站视觉原型」这张票的产出（map：[个人站自管化](https://github.com/Lkyloveaw/lkyloveaw-home/issues/20)）。

票：<https://github.com/Lkyloveaw/lkyloveaw-home/issues/21>

它记录**这次视觉方向是怎么定的**：问了什么问题、给了几个候选、**赢家是哪个、为什么**，
以及落选的东西去哪了。产品实现已进 `src/views.ts` 与 `public/style.css`。

---

## 1. 要回答的问题，以及为什么选「面板」当载体

map Notes 第 6 条已经定了大方向：**整站风格 = B+C 混合**（数据面终端等宽化 / 正文面纸感阅读化）。
所以这次要判的不是「用不用等宽 / 衬线」，而是一个更具体、也更容易判错的问题：

> **一个「一眼看出什么坏了」的运维面板，该用什么信息层级和主操作？**

载体选了**已存在的 `/status`**（而不是新造一个页面）。这是原型技能里的 **sub-shape A**：
数据获取、查询参数、鉴权全部保留，**只换渲染子树**。理由很实在——
原型在隔离的空页面里「每个变体看着都挺好」，只有贴着真实页头、真实数据、真实密度才暴露问题。
面板也是全站信息密度最高的一面，视觉方向在这里最容易被证伪。

## 2. 三个候选，争的是「信息层级」不是配色

按技能要求，变体必须**结构不同**（「只改颜色或文案是墙纸，不是原型」）：

| | 变体 | 立意 | 主操作 | 什么时候它更好 |
| --- | --- | --- | --- | --- |
| `A` | **值守台** | 故障占满版面，健康折叠成一行 | **扫** | 常驻标签页/大屏，只想立刻知道「什么坏了」 |
| `B` | **卡片墙** | 每个系统一份自洽的小报告，网格对齐 | **比** | 横向比谁快、谁 P95 差、谁连续稳定久 |
| `C` | **时间轴优先** | 所有目标的行连成一片共享时间轴 | **定位** | 排查「昨晚那段时间到底怎么了」 |

三者真的分歧在**第一等公民是谁**：A 是「故障名单」，B 是「每个系统」，C 是「时间」。

## 3. 赢家：`B`，且**按用户反馈融合过一次**

第一版 B 的每张卡顶部是**可用率环**（内联 SVG 圆环）。用户看过后的反馈是：

> 「BC 融合一下。B 的可用率换成 C 的格子连成一片。」

于是 B 的形态定为 **卡片 + 定宽时间格带**：

| | 融合前 | 融合后（**定稿**） |
| --- | --- | --- |
| 卡顶部主视觉 | 可用率环（一个总数） | **定宽时间格带**（旧 → 新） |
| 看得出「什么时候坏的」 | ❌ 环只给一个百分比 | ✅ 逐格可见 |
| 卡与卡横向可比 | 环大小一致 | 格带宽与格数**完全一致**，比的是图案 |
| 可用率百分比 | 环的圆心 | 格带下方小字 |

**为什么这次融合是有道理的，而不只是「两个都想要」**：
环回答的是「好到什么程度」（一个数），格带回答的是「什么时候坏过」（一个形状）。
在**同一张卡**里，后者是前者的超集——一个百分比可以由格带推出来（下方小字就是），
反过来推不出来。所以换掉环是**净增益**，而不是取舍。

### 落了什么，为什么

- **A 的「故障名单优先」落了**：它是很好的大屏形态，但这个站是**一个人偶尔看一眼**，
  不是值守大屏。没有任何故障时 A 几乎是一张空页——而「一切正常」恰恰是绝大多数时刻。
- **C 的「共享时间轴」落了（但它的格带被采纳了）**：C 的骨架把时间当第一轴、目标是行，
  单目标的细节（P95、连续可用、URL）被压扁。B 保留了「每系统自洽」这个更常被问的问题，
  同时把 C 最值钱的那块（格带）拿了进来。

## 4. 两个实现决定不是随手定的

1. **格数固定（`CELL_STRIP_LEN = 56`），不按实际探测点数渲染。**
   否则刚部署时只有两三次探测，格带会缩成一根小条——看起来像布局坏了；
   更要紧的是**各卡格数不一致就没法横向比**，而「横向比」正是卡片墙的全部意义。
2. **缺失的历史画成空心格（`.cell-missing`），不是留白、更不是假装 `up`。**
   库里确实没有那段时间的记录，画成任何状态都是撒谎。窗口填满后空心格自然消失。

这两条都写在 `src/views.ts` 的 `cellStrip()` 注释里，紧挨着代码。

## 5. 落地：赢家是**重写**进产品代码的，不是搬运

原型是在「无测试、无错误处理、只为回答一个问题」的约束下写的（技能明确要求如此），
**直接搬进产品会把那些约束一起搬进去**。所以：

| 产品文件 | 改了什么 |
| --- | --- |
| `src/views.ts` | `statusPage()` 的卡片重写：头部 = 点 + 名称 + **状态徽标**；主视觉 = **格带** + 说明行；延迟曲线保留。新增 `cellStrip()` / `STATUS_TEXT` / `STATUS_CLASS`；删掉被取代的 `timelineBar()` |
| `public/style.css` | 新增 `.badge`（三档配色）与 `.cell-strip`（含 `.cell-missing`）；删掉 `.tl` / `.tl-cell` / `.tl-empty` |
| `src/views.ts` 的 `statusDot()` | **不动**，但 `.dot` 的三档形状改成**真的不同形状**（圆 / 方块 / 三角 / 空心圆），并把原先的 `box-shadow` 光晕去掉——那是装饰，而形状是**信息** |

**保留的兼容契约**（`status.js` 与面板检查靠它）：
`#status-root` · 每卡的 `data-target` / `data-state` · 格带的 `data-timeline`（**整块重建**，
因为空态与非空态结构不同）· 格带 `title` 与状态同步生成。

**一处落地时写错、真机验证才抓到的 bug**：徽标最初输出 `badge ${state}`，
于是类名是 `badge up` / `badge degraded` / `badge down`，而 CSS 只认 `.badge.ok/.warn/.bad`
——**徽标一个颜色都没上**，而且**肉眼看不出是 bug**（只是「看起来素了点」）。
根因是**状态值与 CSS 类名不是一套词**（领域状态是 `up/degraded/down`，样式类是 `ok/warn/bad`，
`statusDot()` 早就在做这个映射，我写徽标时漏了）。
修法是抽出 `STATUS_CLASS` 复用同一张表。

> **它值得记一笔的原因**：这类错只在**压平 HTML 后按类名断言**时才现形。
> 我第一次 grep 出来的结果是 0，但那是假阴性——HTML 是多行的，`grep` 按行匹配，
> `<div class="target-head">` 那一行后面根本没有内容。**用 grep 验多行 HTML 会一直骗人。**

## 6. 验证

已在本机真跑（`npm run build` + 一个带临时 `SESSION_SECRET` 的 `node dist/server.js`）：

| 检查 | 结果 |
| --- | --- |
| `tsc --noEmit` | 0 错 |
| `npm run check:chart`（含 panel-check） | **21/21 全过** —— 证明 `status.js` 的契约没被改坏 |
| 产品 `/status` | HTTP 200，含 4 个 `.cell-strip`、4 个 `data-timeline`、`#status-root` 在 |
| 每卡格数 | **56 / 56 / 56 / 56**（定宽成立） |
| 格带分布 | 42 空 + 14 实（每档一个：up / degraded / down / down）—— 三档都真的渲染出来了 |
| 三档徽标 | `badge ok` / `badge warn` / `badge bad` 各 1；无数据徽标 1 |
| 三档形状 | `.dot.bad` 的 `clip-path: polygon(50% 0, 100% 100%, 0 100%)` 在 CSS 里生效 |
| 旧类清除 | `tl-cell` / `tl-empty` / `class="tl"` 在产品页上**全部为 0** |
| 原型隔离 | 产品页 `pv-bar=0`；`?variant=A` 不再有任何特殊行为 |

### 未验证的部分（诚实登记）

- **对比度是估的，不是算的。** 浅色与深色的次要文字、状态色都是按「明显不够就读得吃力」
  的方向调的，**没有跑 WCAG 对照脚本**把每一对前景/背景的比值算出来。
- **没有真机浏览器 PoC**：所有验证都是 HTTP 层与产物层（curl + 产物断言），
  没有目视过渲染结果，也没有测过窄屏断点与打印样式。
- 这套 token 目前只落在**面板**（`public/style.css`）。首页 / 文章 / 管理台的视觉
  仍沿用原样式——那部分归后续批次，不在本票。

## 7. 落选的东西去哪了

**抛弃分支 `prototype/status-variants`**（已推送到远程）：

```
src/prototype/status-variants.ts   三变体 + 底部切换条 + 页面组装（主内容区零共享）
src/prototype/prototype-css.ts     原型专用 token 与样式（只有 token，没有布局类）
src/prototype/NOTES.md             交接说明：变体在争什么、两个实现要点、未验证处
prototype/                         第一轮的单套设计静态页（已被三变体取代，留作对照）
scripts/prototype-dev.js           开发启动器（无 .env 时生成临时密钥）
```

**为什么留在分支而不是留在主分支、也不是删掉**：技能 §6 的判据是
「整套变体是这次决定的**主源**」——留主分支会烂掉并误导下一个读者，删掉则丢掉证据链。
所以它进抛弃分支，主分支只留这份决议与产品实现。

**主分支上不留**：`src/prototype/`、`prototype/`、`scripts/prototype-dev.js`、`?variant=` 分支、
底部切换条 —— 一条都不留。

## 8. 边界

- 本票**只定面板的视觉与信息层级**。整站其余页面（首页 / 分享 / 文章 / 登录 / 管理台）
  的视觉归后续；`docs/write-path-auth-decision.md`（#25）定的管理台页面形态**未受影响**。
- **不定**配色 token 的全局推行方式：本票落地在 `public/style.css`，
  那份文件里仍有原主题的 `:root` 变量，两套东西**暂时并存**。整站统一是后续批次的事。
- 本票**不改** `status.js` 的行为契约，只改它渲染所依赖的标记（并已用 panel-check 证明没改坏）。
