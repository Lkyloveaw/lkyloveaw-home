# 5. 文章存 SQLite，不存 Markdown 文件

日期：2026-10-17
状态：已采纳

> 2026-10-22 注：Docker 部署已从仓库移除（**仅 systemd**），本文提到的 `docker-compose.yml`
> 与 `:ro` 挂载**不复存在**。「文章真源 = SQLite」这个决定不受影响——现在连挂载都没有了，
> `content/` 只作为首次导入的来源存在。

## 背景

「分享」栏目原本是 `content/` 下的 Markdown 文件（front-matter 六个键 + 正文），由 `src/content.ts` 读。
这套东西上压着一个硬约束：`docker-compose.yml` 把内容目录**只读**挂进容器（`./content:/app/content:ro`），
而且那句注释是**有意**写的——「目标清单与内容：改完重启容器即可生效，容器内只读」。
所以「网页上写、改、发文章」这件事一开始就没有落脚点，必须先回答**谁是权威**。

map #30 在 [文章真源与草稿 / 发布语义](https://github.com/Lkyloveaw/lkyloveaw-home/issues/32) 上把这个问题摆开。
判据不是偏好，是用户自己给的两条：**编辑入口只有网页**（不再直接用编辑器改这些文件），
但**「退回上一版」和「看清改了什么」必须真的能用**。（第三条候选「灾难恢复」不构成判据——
它已经被 `runBackup()` 的整库备份覆盖了。）

## 决定

**文章的真源是 `articles` 表**（与目标、账号同一个 SQLite）；`content/*.md` **只在首次导入时读一次**，
此后被完全忽略。每次保存留一行 `article_revisions` 全文快照。

## 理由

两条判据同时成立时，两个候选的代价差得很清楚：

- **选文件**：回溯只能靠 git，而「**谁 commit**」没有答案——要么靠人记得手动 commit
  （忘了就没有回溯），要么给单容器镜像装 git + 配 identity + 每次保存自动 commit + 处理并发写。
  而既然不再直接改文件，文件就只剩「能被 git diff」这一个好处，撑不起上面那两笔成本。
- **选数据库**：修订表由应用自己保证；写路径直接复用 [#25](https://github.com/Lkyloveaw/lkyloveaw-home/issues/25)
  的守卫 / 事务 / CSRF；**部署一处都不用改**——首次导入只需要**读**，`:ro` 挂载可以原样保留。

顺带与姊妹图一致：map #20 已经为 `targets.json` 与 `.env` 立过**同一条规则**（`CONTEXT.md` 的「首次导入」词条），
文章走同一条，不是新发明的机制。

**看过主流方案后仍然选它**（WordPress `wp-admin/includes/schema.php`、Ghost
`ghost/core/server/data/schema/schema.js`）：两家自托管博客引擎**都是数据库**，
而且 Ghost 支持的正是 SQLite。摘要存列、新建默认草稿、修订表存全文快照，三条都与两家一致。

## 影响

- **代价被明确接受**：丢掉 git 原生的**行级** diff。规格
  [#48](https://github.com/Lkyloveaw/lkyloveaw-home/issues/48) 第一版只给「版本列表 + 逐版全文 + 退回」，
  行级 diff 归后续；这是本次唯一真正让出去的东西。
- **`CONTEXT.md` 的「首次导入」词条扩写为「同样适用于文章」**——目标 / 设置 / 文章三处共用一条规则。
- **`docker-compose.yml` 的 `:ro` 挂载保留不动**，只改那句注释（文章改完在网页上就生效了，
  不再是「改完重启容器」）。
- **备份与恢复不变**：文章与修订跟探测历史在同一个 SQLite 文件里，`runBackup()` 一并覆盖。
- **迁移是一次性的**：既有两篇在 `articles` 表为空时导入（日期 / 标签 / 手写摘要原样保留），
  此后改 `content/*.md` 不产生任何影响，只打一行警告。
- **读面的对外契约不变**：`/posts/<slug>` 与 `/tags/<tag>` 照旧；既有两篇的 URL 是迁移的验收条件。
- 这条决定**不等于**「文章不能导出」：以后若要一份人类可读的镜像（单向导出，不作为输入），
  属于新增能力，与真源无关。
