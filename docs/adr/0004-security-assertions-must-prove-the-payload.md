# 4. 安全断言必须先证明载荷出现

日期：2026-10-15
状态：已采纳

## 背景

e2e 套件里曾经有这样两条「安全」断言：

```
!/<script>alert/.test(body)
!/href="javascript:/.test(body)
```

它们**永远通过**——因为被测页面里本来就不含这些字面量。这两条**不注入任何载荷**，
所以它们不检验任何东西，却让「38 项通过」看起来很有底气。

这是一个比「没有测试」更糟的状态：**没有测试**时人会谨慎；**恒真的测试**会给出虚假信心，
反而促使人放行。

## 决定

**每一条安全断言都必须先证明载荷真的出现在输出里，再断言它没有被当成代码执行。**

具体做法：

1. 把攻击载荷写进**真实数据通路**（文章 frontmatter / 正文 / URL 查询参数 / 环境变量），
   而不是构造一个字符串去比对；
2. 先断言「载荷以**转义后的形态**出现在页面上」（如 `&lt;script&gt;`），
   这证明**注入确实生效、渲染路径确实走到了**；
3. 然后才断言「没有可执行的形态」（如 `<script>alert(1)</script>` 不出现）。

对照项（control group）同理：验证「换密钥后旧 cookie 失效」时，必须先证明「密钥不变时旧 cookie 有效」，
否则那条断言可能是恒真的。

## 理由

**没有第 2 步，第 3 步就是恒真的。** 只要载荷没进到页面里（比如字段改名、模板路径变了、
测试写错了字段名），第 3 步必然通过，而人会读成「转义没问题」。

还有一条容易写错的推论：**转义之后，「危险关键词」仍然会出现在页面上**。
比如载荷 `" onmouseover="alert(1)" x="` 被转义成 `&quot; onmouseover=&quot;…` ——
` onmouseover=` 这个子串**依然存在**，但它已经无害（`&quot;` 不是属性分隔符）。
所以正确的断言是「**带真实引号的属性断裂序列不存在**」，而不是「页面上没有 `onmouseover`」。
写错方向会得到一条**恒假**的断言（永远红），也同样无用。

## 影响

- e2e 的断言数量会因为「证明 + 否定」成对出现而增加，值得。
- 覆盖 7 个注入面：文章标题/摘要/标签、正文、标签路由的 `<h1>` 回显、登录页 `next` 隐藏域、
  目标名、错误文案上屏、站点标题。
- 新增断言时要问自己：**「如果我把被测代码改成完全不转义，这条会红吗？」**
  不会红的断言等于没写。
- 同样的纪律适用于别的「否定式」断言：断言「不发生 X」之前，先证明「能发生 X 的条件已成立」。
