# 6. 为富文本编辑器引入前端构建步骤与依赖

日期：2026-10-17
状态：已采纳

## 背景

本仓库反复声明过「**无构建步骤**」「**不引前端框架**」「**尽量不引依赖**」，而且这条约束是被写进
map 的「既有约束延续」里的，不是随口一提。

文章编辑器形态在 [#34](https://github.com/Lkyloveaw/lkyloveaw-home/issues/34) 上定稿时选了**富文本**。
富文本的成品**必须**站在一个编辑器库上：

- 原型用的是 `contenteditable` + **`execCommand`（已被标准废弃）**。它能出第一版手感，
  **不能当成品的地基**——表格编辑、粘贴清洗、撤销栈、选区处理这些都不该由我们手写。
- 原型的反向转换器（HTML → Markdown）**手写了 342 行才到「原型级」**，而那已经是我们不想维护的东西：
  同一份转换器在样本上「表格 5/5 保住」，换一份输入就 **5 行 → 0 行**。

## 决定

**为编辑器的编辑面引入前端构建步骤与 WYSIWYG 依赖**（ProseMirror / TipTap 系）。
正文以**结构化文档 JSON** 落库，读面用**同一套 schema 在服务端生成 HTML**
（细节与理由见 `docs/editor-shape-decision.md` §5）。

## 理由

- **替代方案只有「手写编辑器」**，而它的代价已被原型量化：342 行转换器 + 托盘一堆交互，
  天花板却更低（真实输入上 5/6 项丢失）。
- **「无构建步骤」这条约束的初衷是「不为了渲染只读页面引入工具链」**。编辑面是一个**交互密集**的界面，
  它与「服务端渲染只读页面」是两件不同的事。约束可以**只在这一处破**，而不是整站放弃服务端渲染。
- 破得起的判据：读面（首页 / 列表 / 文章页）**一行都不受影响** —— 仍是服务端渲染、禁用 JS 也能读。

## 影响

- **读面不受影响**：仍然是服务端渲染，禁用 JS 也能读。这是这条决定能被接受的关键。
- **写需要 JS**：修订 `docs/article-write-api-decision.md` §5.2 的「禁用 JS 仍可写」。
- **多一条构建流水线**：打包产物只服务编辑面；`public/` 多一份构建输出，
  闸门是**精确路径匹配**的白名单，新增静态资源要显式加进去（否则编辑页的脚本会被闸门挡掉）。
- **依赖数量与体积上升**；`npm run verify` 的构建环节必须覆盖新产物——
  否则「产物没构建」这类问题会静默漏过（本仓对「静默降级」的态度是不接受）。
- **安全属性以另一种方式保住**：schema 里**不启用 raw HTML 节点**，读面可渲染的标签集是闭集，
  与今天 `markdown-it` 的 `html: false` 等效——不需要引入服务端 HTML sanitizer。
- 具体选型（直接 ProseMirror 还是 TipTap）与扩展集**不在本 ADR**，属于实现。
