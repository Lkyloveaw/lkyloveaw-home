# 权限模型：管理员与只读的边界、首个管理员、防锁死

本文件是「权限模型」这张票的产出（map：[个人站自管化](https://github.com/Lkyloveaw/lkyloveaw-home/issues/20)）。

票：<https://github.com/Lkyloveaw/lkyloveaw-home/issues/24>

回答五个问题：**只读能看什么**、**role 存在哪**、**首个管理员怎么产生**、
**角色怎么改**、**怎么防锁死**。

本票**只产决定**，不写码。落地方案由 map 的「实现批次怎么切」票切成实现票。

## 0. 结论速览

| 问题 | 结论 |
| --- | --- |
| 只读能看到什么 | **等于今天登录用户的只读面**（首页 / 分享 / 关于 / 面板）+ 改自己的口令；管理台整块不可见也不可用 |
| role 存在哪 | `users.role` 一列（`TEXT`，`'admin'` / `'readonly'`，带 `CHECK`）；**DB 是唯一真源，不进 cookie** |
| 角色变更怎么生效 | 每请求随 `getAuthState` 查库 → **下一个请求就生效**；不动 `token_version`、不踢该账号会话 |
| 首个管理员 | 补列迁移时**既有账号一次性升为管理员**；零账号首启用环境变量建的首个账号 = 管理员；此后**新建账号默认只读** |
| 谁能改角色 | 管理台能改**别人**，不能改**自己**；CLI `--role` 是权威与恢复通道 |
| 防锁死 | 拒绝任何把「启用中的管理员数」降到 0 的操作（网页与 CLI 同一守卫）；启动时检出零管理员 → **醒目告警，不自动修** |

## 1. 只读 vs 管理员：能力边界

**只读 = 今天那个已登录用户的全部只读面**，一个字都不减：

| 面 | 只读 | 管理员 |
| --- | --- | --- |
| `GET /`、`/posts`、`/tags/:tag`、`/posts/:slug`、`/about` | ✅ | ✅ |
| `GET /status`、`/api/status`（面板与可用性数据） | ✅ | ✅ |
| `POST /password`（改**自己的**口令） | ✅ | ✅ |
| `/healthz`（匿名白名单，与角色无关） | ✅ | ✅ |
| 管理台（`/admin` 及其下全部页面与写接口） | ❌ **整块不可用** | ✅ |
| 账号列表 / 备份列表与产物 / 站点设置 / 目标的写操作 | ❌ | ✅ |

**为什么只读正好等于「今天的登录用户」**：今天闸门是**扁平**的（`docs/accounts-decision.md` §7 当时明确不做角色差异），
所有账号看到同一套面。把只读定义成这套面，等于「引入角色」对现有用户**零回归**，
差异只多出一个「能不能写」——需要回归测试的面因此最小。

**为什么不让只读看备份与账号**：这两块是运维面。备份列表泄漏备份路径与节奏，账号列表泄漏账号名，
都不是「读站点」需要的；而第一版并没有「只读用户也要排障」的真实需求。等真有这条需求再开票，不要预先放宽。

**第一版不做「只读视图」**：只读进不了管理台，所以 #23 要定的不是「只读视图长什么样」，
只是**不可见的呈现形态**（入口不渲染 / 403 / 404）——这是本票刻意留给 #23 的那一格。

**刻意不做差异的一面：草稿**。`draft` 过滤发生在**内容层出口**（`src/content.ts:131`），
对所有角色一视同仁；map 迷雾里「只读能否看未发布内容」因此**不适用**：没有一个面能看见未发布内容。

**边界（本票不定）**：只读访问管理台时的具体状态码与入口渲染归 [管理台的信息架构与入口](https://github.com/Lkyloveaw/lkyloveaw-home/issues/23)；
写接口的鉴权判定函数形态与错误呈现归 [写路径的鉴权面](https://github.com/Lkyloveaw/lkyloveaw-home/issues/25)。

## 2. 存储：`users.role`，DB 是唯一真源

```sql
-- 新库：建表时就带上
role TEXT NOT NULL DEFAULT 'readonly' CHECK (role IN ('admin','readonly'))

-- 旧库：沿用 src/users.ts:94-98 的「PRAGMA table_info 检出 + ALTER」风格
ALTER TABLE users ADD COLUMN role TEXT NOT NULL DEFAULT 'readonly'
  CHECK (role IN ('admin','readonly'));
UPDATE users SET role = 'admin';   -- 一次性：此刻库里的都是「既有账号」
```

**为什么 `TEXT` 而不是 `INTEGER 0/1`**：取值直接就是领域词（`CONTEXT.md` 的**管理员 / 只读**），
`SELECT` 出来不会记反，写接口与日志里也不需要一张常量对照表。多几个字节在这个量级上没有意义。

**为什么加 `CHECK`**：非法值（`'admni'`）会被**库**挡住，而不是靠每个写路径各自记得校验。

**为什么迁移时 `UPDATE users SET role='admin'` 是无条件全表**：能跑这条语句的唯一时刻，
就是「role 列刚被补上」的那一刻——此刻库里的每一行都必然是列诞生之前就存在的账号。
不需要、也无法再区分「更早的账号」。

> **已知后果（写在这里，不藏在代码里）**：**停用中的既有账号也会成为管理员**。
> 它登不进来，所以眼下无害；但日后有人对它执行 `--enable`，它会**直接是管理员**。
> 这是「既有账号 = 当时信任的人」这条规则的自然外延，接受；若要改成「只升启用中的既有账号」，
> 改的是上面那一条 `UPDATE` 的 `WHERE`，代价一行。

**role 不进 cookie**（对 `docs/session-decision.md` §5 的修订，见 §6）：
真源只有库里那一列，cookie 载荷仍是 `uid + exp + pv`。理由是**第二份真相**——
角色若进了载荷，一次降级就得等旧 cookie 过期才真正生效，而库里的真相已经变了。

**取角色的成本是零**：闸门每请求本来就调一次 `getAuthState(uid)`（`src/auth.ts:100`、`src/users.ts:207`），
把 `role` 并进同一条 `SELECT` 即可——**不新增查询次数**，也不新增失败模式。

**实测证据**（本票验收，SQLite 真跑）：

| 断言 | 结果 |
| --- | --- |
| 旧库上 `ALTER ... ADD COLUMN role ... CHECK(...)` 被接受 | ✅ |
| 迁移后既有两行（含一行停用）全为 `admin` | ✅ |
| 新账号不写 role 落到 `'readonly'` | ✅ |
| 写入非法角色被拒：`CHECK constraint failed: role IN ('admin','readonly')` | ✅ |
| 零行表上跑 `UPDATE users SET role='admin'` 不报错、0 行受影响 | ✅ |

## 3. 角色变更的判定表

守卫是**一个**函数（住 `src/users.ts`，纯库函数、不过 HTTP），
**网页写路径与 CLI 共用同一个**——两条通道规则不一致时，CLI 就成了绕过守卫的后门。

| 操作 | 目标 | 结果 | 判据 |
| --- | --- | --- | --- |
| 降级 `admin → readonly` | 别人 | **拒绝** | 启用中的管理员数 = 1（且目标是其中之一） |
| 停用 `enabled 1 → 0` | 别人（`role = admin`） | **拒绝** | 启用中的管理员数 = 1 |
| 降级 / 停用 | **自己** | **拒绝** | 本票定：管理台不能改自己的角色（§4） |
| 提权 `readonly → admin` | 任何人 | 允许 | 恢复通道，永不设卡 |
| 启用账号 `enabled 0 → 1` | 任何人 | 允许 | 恢复通道，永不设卡 |
| 新增账号 | — | 允许 | 角色默认 `readonly`（最小权限） |
| 重置口令 / 改自己的口令 | 任何人 | 允许 | 既有行为：递增 `token_version`，踢掉该账号全部会话 |
| 降级 / 停用 | 非管理员，或管理员数 ≥ 2 | 允许 | 不减少「启用中的管理员」到零 |

**守卫只数「启用中的管理员」**（`role='admin' AND enabled=1`）。
停用的管理员登不进来，若把他算作「还有管理员」，守卫就等于形同虚设——
一处自锁会被伪装成一处安全。

**角色变更不踢会话**（与改口令区分开）：`role` 每请求查库，降级/提权下一个请求就生效，
所以**不需要** `bumpTokenVersion`。要立刻踢人是**改口令**的动作，不是改角色的动作。

## 4. 首个管理员怎么产生（三个入口，一张表）

| 入口 | 得到的角色 | 理由 |
| --- | --- | --- |
| **补列迁移**：库里既有的账号 | `admin` | 这些账号是闸门上线后建的，个人站账号以个位计（`docs/accounts-decision.md` §1）；只读的意义是把访问权**给别人**，自己必须是管理员 |
| **零账号首启**：环境变量建的第一个账号 | `admin`（**显式指定**，不能靠默认值） | 表里一个账号都没有时，若首个账号是只读，**全新部署开箱即锁死**管理台。注意 `ensureFirstUserFromEnv` 已经保证「表非空时环境变量被完全忽略」（`src/users.ts:232`），所以这里不会变成后门管理员 |
| **管理台 / CLI 新建账号** | `readonly` | 最小权限。要给人管理权，是一次**显式**的提权动作 |

判断顺序上，「新建默认只读」管的是**有管理员之后的日常新增**，首启是它的**例外**，
例外必须显式写在调用点上，不能靠 `DEFAULT` 蒙出来。

**CLI 增一个 `--role admin|readonly`**（`src/cli/passwd.ts` 今天只有
`--list` / `--user` / `--password` / `--revoke-sessions` / `--disable` / `--enable`），
`--list` 增印角色列。CLI 是**恢复通道**：提权与启用两个方向永不被守卫拦，
所以「真的锁死了」（只可能由手工改库造成）总有出路。

**管理台可以改别人的角色，不能改自己的**：能改别人，换角色才不必每次都 SSH 敲 CLI；
不能改自己，是因为「把自己降成只读」是最容易误触、后果最直接的自锁路径，直接不给这个按钮。
（守卫本来也会拦「把最后一个管理员降级」，但连"第一个管理员把自己降了、还剩一个同事"这种
需要先想清楚的操作，也不该在一次误点里发生。）

## 5. 零管理员状态：只告警，不自愈

进入「零管理员状态」（库里没有 `role='admin' AND enabled=1` 的账号）只可能来自**手工改库**：
守卫拦住了全部 API 通道，CLI 的提权/启用方向也不会造成它。

**启动时检出 → `console.warn` 醒目告警 + 打印修复命令**（`node dist/cli/passwd.js --user X --role admin`）。

**为什么不自动提权**：静默改权限比锁死更难排查——运维会看到「权限自己变了」而找不到是谁改的。
与仓库既有取舍「**失败要显眼不要静默降级**」一致。

**为什么不拒绝启动**：按 `docs/session-decision.md` §6 的判据「**重启能不能自愈**」——
零管理员是**运行状态**（服务本身健康，只是没人能进管理台），拒绝启动会进
`restart: unless-stopped` 的**崩溃重启循环**，把真正的原因刷没。
这与「`users` 表为空允许启动 + 告警」是同一条判据的两个实例。

## 6. 对既有决定的显式修订

本票**推翻**两条既有结论，按 map Notes 的要求显式登记，不偷偷改：

| 既有决定 | 原文 | 本票 |
| --- | --- | --- |
| `docs/accounts-decision.md` §7 | 「本轮不做角色/权限差异：`users` 表**不加 `role` 列**，等真有需要区分的能力再说」 | **推翻**：`role` 列建起来。那「真实需要区分的能力」就是**管理台**——只读的人不该能改目标、账号、设置、备份 |
| `docs/session-decision.md` §5 载荷表 | `role` **不放**，理由是「`users` 表已定不加 `role` 列，放进去是一个永远为空的字段」 | **结论不变（仍不放），理由换掉**：库是唯一真源，放进载荷 = 降级/提权后旧 cookie 在过期前仍自称管理员。与 `username` 同理（第二份真相） |

不动的部分：`pv`（`token_version`）仍是**唯一**的「一次踢掉全部设备」通道，
CLI `--revoke-sessions` 保留（map Notes 第 2 条）。
