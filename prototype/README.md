## 一句话风格

**数据面终端化 + 正文面纸感化**（map Notes 第 6 条的 B+C 混合）。分界不是「页面」，是「这块内容在回答什么问题」：

| | 数据面（面板 / 管理台 / 登录 / 顶栏导航 / 元信息） | 正文面（首页 lede / 分享列表 / 文章 / 关于） |
| --- | --- | --- |
| 字体 | `--font-mono`（等宽） | `--font-serif`（衬线） |
| 气质 | 紧凑、对齐、`tabular-nums`、格子感 | 宽松（行高 1.95）、行宽 ≤ 40 字、克制 |
| 字号 | `--fs-xs` ~ `--fs-2xl` | 正文 1.06rem，标题走 sans |
| 底 | 卡片 + 1px 边框 | 无框、直接落在页面上 |

**为什么正文用衬线**：中文长文里，衬线 + 大行高 + 窄行宽是唯一同时管住「跳行」和「累」的组合。
标题仍用无衬线，是为了让 `h2` 在长文里**一眼能被扫到**（衬线正文里插一个等宽/无衬线标题，层级立刻出来）。

## 三条硬约束（及它们怎么被满足）

### 1. 不引 webfont —— 只用系统字体

内网站点、无构建步骤，所以**一个字体文件都不加载**。四条栈各带 fallback：

```css
--font-mono:  ui-monospace, SFMono-Regular, "SF Mono", Menlo, Consolas,
              "Liberation Mono", "Noto Sans Mono CJK SC", monospace;
--font-serif: Georgia, "Times New Roman", "Songti SC", "Noto Serif SC",
              "Source Han Serif SC", "Source Han Serif CN", serif;
--font-sans:  -apple-system, BlinkMacSystemFont, "Segoe UI", "Noto Sans SC",
              "Microsoft YaHei", "PingFang SC", "Hiragino Sans GB", sans-serif;
```

覆盖 Windows（Consolas / 微软雅黑 / 宋体）、Android（Noto 系列）、iOS / macOS（PingFang / Songti / Menlo）。
**待你确认的一点**：中文的「终端感」在 Windows 上落到 Consolas + 微软雅黑混排——
`Consolas` **没有汉字**，所以中文会回退到系统无衬线，中英混排的字重会有落差。
想更整齐的话有两条路，都要引字体（与「不引 webfont」冲突）：
① 只给数据面用一个 `Noto Sans Mono CJK SC` 的 woff2 子集；
② 接受落差，靠字号/颜色把层级做出来（当前方案）。
**我默认选了 ②。**

### 2. 禁用 JS 也要能读、能写

- 主题切换 = 三个 `<input type="radio">` + `html:has(...)`，**零 JS**。
  `:has()` 需要较新的浏览器（Chrome 105+ / Safari 15.4+ / Firefox 121+），
  内网现代浏览器没问题；**不支持时自动回退到「跟随系统」**，不会坏。
- 面板曲线 = **服务端渲染的内联 SVG**（原型里是手写的静态 SVG）。
- 破坏性操作的确认 = 原生 `<input type="checkbox" required>`，
  **不是** `confirm()` —— 后者在禁用 JS 时根本不执行，那道防线会消失。
- 打印样式已写：正文面打印时去掉导航/底色，像纸一样。

### 3. 状态三档绝不只靠颜色

`up` / `degraded` / `down` 各带**独立形状**：**实心圆 · 方块 · 三角**，再叠一层文字 `badge`（可用 / 异常 / 故障）。
灰度打印、红绿色盲、以及「一眼扫过」三种场景下都分得清。
`CONTEXT.md` 的**状态**词条明确要求三档不许退化成二值，这条是它的视觉落地。

另有两个刻意的取舍（都在 `status.html` 里能看到）：

- **失败处的延迟曲线是断开的，不是画成 0ms**——0ms 会让曲线看起来「更快了」，与事实正好相反。
- **故障轮次在总体走势上打了红点**——只看曲线的话，「掉下去又弹回来」的那一段会被平均值吃掉。

## 深浅双模

深色是**设计基准**（沿用 `public/style.css` 的既有形态），浅色是覆盖。
两套都定义了完整的语义色，且**状态色在三档下都保持可辨**：

| 语义 | 深色 | 浅色 |
| --- | --- | --- |
| `--bg` / `--bg-card` | `#0e1013` / `#181c21` | `#f6f6f3` / `#ffffff` |
| `--fg` / `--fg-dim` | `#e8eaed` / `#a4abb5` | `#1d1f1c` / `#5c605a` |
| `--ok`（可用） | `#46d07d` | `#1a7f45` |
| `--warn`（异常） | `#e8b93a` | `#8a5a00` |
| `--bad`（故障） | `#ff6b5e` | `#b3261e` |

浅色的状态色**刻意调深**（不是把深色值搬过来）：`#46d07d` 那种亮绿在白底上对比度不够，
做背景块或小圆点时还行，一旦当文字色就不合格。所以浅色用 `#1a7f45`。

## 明确没做的（以及为什么）

- **不做移动端专门布局**：只有 `640px` 断点（砍掉表格次要列、收紧字号）。
  900px 栏宽 + 自动填充网格本来就自适应。
- **不做暗色/亮色的手动记忆**：纯 CSS 方案没有存储，刷新后回到「自动」。
  要记住偏好就得写 JS 或加 cookie——不值得为它破「禁用 JS 也要能读」。
- **不做任何图表库**：曲线是 SVG，`status.html` 里是手写坐标。
- **不做动效**：内网工具站，动画只增加噪音。
- **不碰生产代码**：`public/style.css` 与 `src/views.ts` 一行未改。

### 「两档同等打磨」具体改了什么

核心是：**同一个语义色在两档里各自配到够读**，而不是把一个值抄两遍。

| token | 浅色 旧 → 新 | 深色 旧 → 新 | 为什么 |
| --- | --- | --- | --- |
| `--fg-faint` | `#8b8f88` → `#767b74` | `#6f7780` → `#878f98` | 它要出现在**卡片底**上，而卡片底比页面底亮/暗是两档各自的事实 |
| `--unknown`（无数据） | 跟 faint → `#767b74` | `#5a636d` → `#7d8794` | 「无数据」是**要读的正文色**，不是装饰；`#5a636d` 压在卡片底上太暗 |
| `--warn`（异常） | `#8a5a00` → `#6b4600` | `#e8b93a` → `#edc257` | **琥珀是最脆的一档**：它同时要做文字色和色块，两档都得单独配 |
| `--border-strong` | `#c9c9c0` → `#b3b3a8` | 不变 | 输入框与必勾确认框**靠它自己站住**，不该依赖「里面有个白卡片」才看得见 |

> ⚠ **一个真陷阱（已踩过并修好）**：`html:has(#theme-dark:checked)` 与 `:has(#theme-light:checked)`
> 那两个**手选**主题块是**独立写死的一套值**，它们**不跟 `:root` 走**。
> 改 `:root` 而忘了同步这两块，症状是「改成 X 之后看着正常，一按『深』又变回旧配色」——
> 我第一次改就漏了，现在三处已一致（`:root` 浅色 / `prefers-color-scheme` 深色 / 两个 `:has()`）。
> 落地到 `public/style.css` 时，**这三处必须当成一件事改**。

### 「管理台密度」的做法

`admin-targets.html` 现在是**两张图叠着**：

1. **一览表**（新增）：`状态 · id · 名称 · 分组 · 预期 · 历史行数 · 操作` —— 列对齐，可以横向比。
   最后一行「历史行数 = 0」是唯一显示**删除**按钮的那种目标。
2. **编辑卡片**（保留）：字段直接可编辑，不点多一次。表格里的「编辑 ↓」是锚点跳转，**不需要 JS**。

形式和新增表单都放宽到 52rem、两列最小 210px，一行能并更多字段。

**如果你要的是「只剩表格」**（点编辑才展开行），说一句——那是另一种结构，改动比上面这一版大，我没有替你选。

## 一个诚实的缺口

上面那张「两档同等打磨」的表里，**对比度是估的，不是算的**。
本会话没有可用的命令通道（`ops_bash` 缺 bash IPC 兼容收据、`pwsh` 被执行策略挡在 `prepare-workspace.ps1` 前），
所以我无法跑一个 WCAG 对比度脚本把每一对前景/背景的比值算出来。

我按「明显不够就读得吃力」的方向调了上面四个 token，但**没有验证**：
`--fg-faint`、`--unknown`、`--warn` 与它们各自会压上的底色（`--bg` / `--bg-soft` / `--bg-card` / `--warn-bg` / `--bad-bg`）
是否真的都过 4.5:1（正文）与 3:1（非文字元素）。
